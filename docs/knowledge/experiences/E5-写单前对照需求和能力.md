# E5 写单前对照需求和能力

## 怎么做

写单前列出：目标仓库里管这件产出的需求文档和编号、已经有的能力（命令、代执行动作、插件）。单里逐条写怎么满足或为什么不用。产出要给 Kun 看的（卡、报告），这一步不能省。

再做三步：

1. 列出的现成能力核对到接口：新做法需要的输入，现有端口给不给。看代码里的签名和调用处，不凭名字推断。
2. 单里依赖的外部工具能力（各家 agent 的 CLI、网关、Orca）开单前在本机实测一次，结果写进「背景和目标」。涉及几家的每家都测；没测过的不写成 DoD。
3. 开单前让另一个模型拿草稿和代码，找 DoD 之间、DoD 和约束之间做不到一起的地方；找到的先改草稿或问 Kun，再开单。

## 为什么

ws#122 一分钟写成，违反了现成的 approval-card 需求，也没用同一天刚交付的 sync_app，返工的三处全是现成的东西。

ws#280 列了挑选端口，却没核对它给不给活号，DoD 又写了核心不许改，执行者做不出来，只好等 Kun 同意改核心。ws#283 只实测了 Claude，DoD 却要求 Codex 也不加载个人配置，Codex 的 CLI 做不到，又等 Kun 选一次。两次都是写单时多看一眼接口、多测一家就能发现的，预审能在开单前把这类矛盾挑出来。
