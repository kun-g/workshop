# 写单没核到接口、没实测外部工具，活在跑时又改了 DoD

**结论：写单时列出的现成能力要核到接口，单里依赖的外部工具能力要先在本机实测，开单前让另一个模型拿草稿和代码找做不到一起的地方；活过了接单以后要改 DoD 或约束，等它停下，先改 issue 正文，再登记回答。**

11-19 协调对话在同一个会话里开了 ws#280 和 ws#283，两张单各让执行者白跑一轮、让 Kun 多回一次话，原因都在写单这一步。

## ws#280：DoD 写了核心不许改，挑选端口却拿不到活号

ws#280 要按活号把执行阶段的活固定分给某个写代码执行者。DoD 第一条原本要求挑法全在插件里、核心不改。写单时没核对挑选端口给不给活号：活第一次进执行时历史轮为空，挑选上下文里没有活号，按活号算做不了（PR #284 正文：「原来挑选端口拿不到活号……按活号算就做不了」）。执行者只好登记等待问 Kun「要不要允许核心改一处：挑选上下文加活号和规则候选名，DoD 第一条相应改写」，Kun 答：

> 同意

之后协调对话在活还跑着的时候改了 issue 里 DoD 第一条的原文。执行者 PR 里照抄的是改之前的那一行，车间 13:51 在 PR #284 上留言把活退回执行：

> 车间合并前 DoD没过，活退回执行：PR 的合并前 DoD 少了一项：新挑法能在规则里按阶段指定（`stage_selectors` 的「执行」）；核心只在挑选上下文里多交活号和规则候选名……

执行者照新原文改了 PR 正文，13:54 合并。

## ws#283：只实测了 Claude，Codex 的 CLI 做不到

ws#283 要写代码的执行者不加载 Kun 本机的个人配置。写单时只在空目录里实测了 Claude 的三种启动方式，DoD 却要求 `orca-codex` 也一样。执行中实测：Codex 交互启动没有忽略个人配置的开关，后台模式加了开关仍加载个人 skill。执行者登记等待问 Kun 怎么做，Kun 选了「本单只做 Claude，Codex 例外」：

> C

issue 正文和 DoD 随后改成 Codex 例外，PR #285 14:06 合并。

## Kun 的原话

协调对话里提了两条建议（DoD 少写实现约束、开单前加一步预审），Kun 答：

> 1，2 认可，我们现在有约束这一个部分么？

问到 ws#283 这类问题时：

> 另外，前面这种 283 的问题，如何预防呢

## 根因

- E5 只要求列出需求和现成能力，没要求核到接口：列了挑选端口，却没看它给不给新做法需要的输入。
- 外部工具（各家 agent 的 CLI）的能力凭推断写进 DoD，只测了一家。
- 开单前没有人拿草稿和代码对一遍，DoD 和约束之间的矛盾到执行时才暴露。
- 活在跑时改 issue 正文，执行者手里那份 DoD 和 issue 原文对不上，车间按原文核对就退回。
