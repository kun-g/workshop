# 教训、经验、规范、原则

车间做事攒下来的东西，分四类放。用词见 `GLOSSARY.md`。

| 类 | 目录 | 是什么 | 谁能写 |
|---|---|---|---|
| 教训（Lesson） | `lessons/` | 一次真碰到的事：发生了什么、代价、根因、以后怎么做。带日期和证据，写完不改 | 协调对话从问题记录提炼；项目经理只往问题记录里记，不直接写教训 |
| 经验（Practice） | `practices/` | 做成过、可以照着做的做法；还不强制 | 协调对话提，有一次成功的证据就能写 |
| 规范（Standard） | `standards/` | 必须照做的具体规定；每条写明落在哪个机制上（检查脚本、关口、命令），没有机制的标「只有文字」 | Kun 认过才算，条目里引原话 |
| 原则（Principle） | `principles/` | 取舍时的判断依据，少而稳，不随一件事改 | Kun 定，条目里引原话 |

## 怎么往上走

- 问题记录（workspace 的 `contexts/projects/workshop/问题记录.md`）→ 教训：由协调对话想清楚根因后写。
- 教训重复出现，或者照它做成了一次，就提成经验。
- 经验违反一次代价高，或者已经证明会被忘，就提成规范，并落到机制上；落成机制后，条目里写机制在哪，不再靠人记。
- 原则只由 Kun 定。规范和原则冲突时，问 Kun。

## 和别处的关系

- `docs/requirements/` 管车间该做成什么样（Kun 认过的行为）；这里管怎么做事。规范要改车间行为的，同时改需求文档。
- `docs/项目经理.md` 是项目经理的手册，引用这里的条目，不重复写。
- 各 agent 的记忆里也有同类规矩；挪进这里以后，记忆只留一行指向这里。

## 文件

一条一个文件，文件名 `YYYYMMDD-短标题.md`（原则和规范不带日期）。开头写类别、日期、出处（会话号、issue、复盘报告），正文先写结论。
