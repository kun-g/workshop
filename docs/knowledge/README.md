# 教训、经验、规范、原则

车间的规矩分两层：
- **用的层**：`AGENTS.md`「规矩」、`docs/项目经理.md`、`docs/协调对话.md` 里带编号的行，一条一句。agent 干活时只读这一层。
- **来历层**：这个目录。写细节、经过和原话，复盘时读。

| 目录 | 放什么 | 文件名 |
|---|---|---|
| `lessons/` | 教训：一件真碰到的事，写经过、证据、原话、根因。写完不改，后续往末尾追加。还在处理的问题（问题记录）也在这里，front matter 多一个 `status` | `YYYYMMDD-短标题.md` |
| `experiences/` | 经验（E）：一条一个文件 | `E<序号>-短名.md` |
| `standards/` | 规范（S）：一条一个文件 | `S<序号>-短名.md` |
| `principles/` | 原则（P）：一条一个文件 | `P<序号>-短名.md` |

教训和条目是多对多：一条经验可以来自好几篇教训（例如 S1 来自 4 篇），一篇教训也可以促成好几条（例如「发版卡没对照现有需求」促成 E1、E5、S1）。引用只从上往下：原则 > 规范 > 经验 > 教训。条目的 `sources` 列下级，可以是教训文件名，也可以是更低一级的编号（比如一条规范由几条经验归纳而来）；教训不反指条目，要查一篇教训促成了什么，搜它的文件名。

## 条目文件怎么写

开头是 front matter：

```
---
id: E1
summary: （和用的层那一行一字不差）
written_in: [docs/项目经理.md, docs/协调对话.md]   # 机制接管或废止后写 []
mechanism: 管住它的命令、检查、关口；没有就写「只有文字」
status: 在用            # 在用 / 机制接管 / 废止
approved: Kun           # 规范和原则写 Kun；经验写 —。不写日期，什么时候批的看 git log
sources: [20261115-发版卡没对照现有需求, ……]   # 教训文件名（不带 .md）或下级编号
---

# E1 发卡前自查第一屏
```

下面两节：「怎么做」写一行装不下的细节；「为什么」写从几篇教训里综合出的结论。改动经过看 git log，文件里不记日期和修订。编号用过就不再复用。

教训的 front matter：

```
---
refs: ws#122、grant-console PR #177   # 出处：issue、PR、会话、报告
status: 未处理                         # 只有问题记录写；取值见下
---
```

问题记录是带 `status` 的教训，一个问题一篇：

- `status` 取值：`未处理`、`已开单 ws#N`（grant-console 写 gc#N，switchboard 写 sb#N，几张单用顿号连）、`手工干预`、`已解决`、`不做`。解决了、不做的不删，改 status。
- 正文三节：「经过」每发生一次一行（时间、现象、证据、影响到的活），同一个问题再发生就往末尾加一行；「根因」协调对话想清楚后补；「去向」写开了哪张单、怎么解决的，或 Kun 说不做的原话。
- `uv run python scripts/check_knowledge.py --open` 列出 status 不是已解决、不做的；加 `--issues` 再用 gh 查「已开单」的单是否已关。

## 用的层怎么写

- 一条一行：`- E11 一句话。`只写什么时候做什么，加上例外和要用的命令。
- 不放原话、日期和事件经过，不超过 80 字。
- 人人要守的写进 `AGENTS.md`，只有项目经理或协调对话要守的写进各自的文件。两个角色都要守的，各写一行，文字一字不差。

`scripts/check_knowledge.py`（在 `scripts/check.sh` 里）核对：用的层不串来历；同一编号文字一致；每个编号都有条目文件，summary、written_in 对得上；sources 指向的教训和条目都存在，而且只引下级。

## 一条规矩怎么来

1. 项目经理把看到的问题记成带 `status` 的教训（问题记录），每天一个 PR。
2. 协调对话想清楚根因，写成一篇教训。
3. 要大家照做的：先记成经验，用的层加一行，`experiences/` 加一个条目文件；Kun 的一次纠正也是这样。已有条目又多了一篇教训支撑的，在 sources 里加上，「为什么」跟着改。
4. 几条经验或几篇教训说的是同一件事、要人人必须照做时，归纳成一条规范，sources 列那几条经验和教训，Kun 过目。规范比经验少，原则更少，只由 Kun 定。
5. 做成机制以后，删掉用的层那一行，条目 status 改成「机制接管」、written_in 改成 []，mechanism 写它在哪。条目文件留着。
