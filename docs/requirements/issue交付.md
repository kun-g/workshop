# issue 交付需求

这份文档管 issue 交付这个插件：一件改代码的活，车间的各个阶段怎么填。阶段和关口本身见 [核心.md](核心.md)；怎么做见设计文档（还没写）；用词以 [GLOSSARY.md](../../GLOSSARY.md) 为准。每条都经 Kun 认过，改之前先问他。

## 要的结果

你在哪里说一句要改什么，车间就把它交付到生产并验收完；你只在说需求、过关口（不可逆、对外、花钱）和要你亲眼看的验收时出现。

不归这里：

- 阶段、关口、等待、失败处理这些所有活都有的，归核心。
- grant-console 的业务，以及它自己的授权卡怎么批，不归车间管。
- 有别人在用的交付对象，上线前要不要先批，以后接进来时再定。

## 要求

### 什么算「说一句」

**R1 你在交付对象的飞书群（例如「grant-console 开发」）或会话里说一句要改什么，或者直接开 issue 打上 `Ready for Agent`，都会变成车间里的一件活。**
为什么：grant-console 现在你就在这几处说需求（grant-console 项目经理的项目记录）；说需求的地方不变，你就不用改习惯。

**R2 你打开这件活的 issue，看得到你的原话、验收标准和验收步骤；要你亲眼看的，在这里写明。**
为什么：验收交给 agent 以后（R6），它照的就是这里写的验收步骤；写不清楚，后面验了也不算数。

**R10 issue 写明它落在哪几条需求上；要新增或改动需求的，先发卡问你，批了才做，合并时同一个 PR 改需求文档。**
为什么：Kun 11-13 担心 issue 没有规范导致项目行为漂移，同意增加「依据」节与需求变更确认（原话「2 加」，见 issue #52）。已有原话确认的引用原话，不重复问。

### 什么算交付到生产

**R3 只有你自己在用的交付对象（grant-console、车间自己），检查和 CI 过了就合并，不等你；两者的上线都交给定时发版流程（见 [定时发版.md](定时发版.md)）。车间自己合并就算交付，验收照常马上做；grant-console 需要上线的改动，等包含该合并提交的一版上线后才算交付，再验收；只含规则配置的文档、测试或 Markdown 路径的活，按 R4 合并即交付。要不要另一家 agent 复核，由规则里的阶段开关定（11-13 起两个都关掉复核）；上线按定时发版 R6 申请指定应用和版本的代执行授权，例外的集群权限需说明具体必要性。**
为什么：你对 grant-console 说过「这个东西目前只有我自己在用啊，就直接上线就行了」（grant-console 项目经理的项目记录）。车间自己合并不等上线：Kun 11-14「目前可以宽松一些，逐渐把检查补上来」；要看上线后效果的活，在 issue 里写亲眼看（R7）。

**R4 只改文档、本机脚本、不用发版的活，合并完就算交付。grant-console 用唯一规则中的路径配置判断文档、测试和 Markdown 变更，重命名两端都要符合；混有服务变更仍等上线。**
11-15 返工确认依据同定时发版 R6；路径枚举不足或读取失败，不能当作无需上线。

**R5 issue 关上，就说明这件活已经验收过了；合并不会把它关掉。**
为什么：grant-console 的 #30 被合并自动关掉，跳过了验收卡（grant-console 项目经理的项目记录）。

### 什么算验收完

**R6 交付后，由另一个 agent（不是写代码的那个）照验收步骤验；过了就收尾，给你发一条不用回的通知。**
为什么：grant-console 11-12 到 11-13 发了 7 张验收卡（Q1828、Q1829、Q1831 到 Q1835），你全部点了通过，没有一次退回；其中 Q1831 到 Q1833 在 08:34:56 到 08:35:01 发出，你在 08:35:55 到 08:36:02 之间连着点完。真正照步骤验的是项目经理，卡只是在确认它验过的结果（ask-kun 的提问记录）。

**R7 只有写明要你亲眼看的（界面、体验、文案这类检查跑不出来的），才发验收卡等你点。**

**R8 你随时回一句「不对」，那件活就退回执行，不管它是不是已经收尾。**
为什么：验收放给 agent 以后，漏掉的问题要等你用的时候才会发现，得有一条一句话就能退回的路。

### 什么算「你只在这些时候出现」

**R9 写代码、审查、修必须改、合并、上线，都不问你；碰到不可逆、对外、花钱的，按核心的 R3 过关口时问你一次。**
为什么：你 11-12 对 grant-console 说过，项目经理「不应该在那边提问题等我看到再回答他，因为我很有可能一个月都不会打开这个页面」（grant-console 项目经理的项目记录）。

**R11 车间程序及执行者在 GitHub 上的动作使用交付对象规则指定的身份。kun-g/workshop 使用 lambdatheory-agent App；kun-g 只代表 Kun 本人亲手进行的动作。grant-console 暂时保持现有身份及批准方式。需要 GitHub 动作的执行轮和程序作业按目标仓库取得 App 令牌，只传给执行动作的进程，不把令牌写入日志或事实，不修改全局身份配置；签发失败时不执行该轮或动作、不回退到个人身份，记录原因并只生成一次通知，通知发送沿用核心的 notices 规则。审查和验收仍遵守现有只读凭据隔离。GitHub 来源只将 kun-g 本人的放行标签和返工评论认作 Kun 的操作，bot 动作不触发放行或返工。Kun 在会话里确认放行后，可以用 `workshop release <活或对象> --quote <Kun 原话> --session <会话号>` 登记，效果等同 Kun 本人打放行标签：未登记对象进入接单，已有卡住或等你的活可继续或返工；quote 和 session 必填且不得为空白，事实记录 channel=session、会话号及原话，why 可查看。**
为什么：Kun 11-13「所有Agent做的行为都用APP自己来做。」；11-14 对会话放行与 GitHub 身份分离方案回答「按推荐」，见 issue #31。

## 衡量

| 指标 | 量的是 | 目标 | 现在 |
|---|---|---|---|
| 每件交付你的消息数 | 你只在该出现时出现 | 逐周降 | 核心的衡量表里那一行，车间还没开始量 |
| 每件活发给你的验收卡数 | 亲眼看的才找你（R7） | 只有写明亲眼看的才有 | grant-console 11-12 到 11-13 每件一张，7 张 |
| agent 验收过了、你后来说「不对」的件数 | 验收放给 agent 漏掉的（R6、R8） | 先只记，逐周看 | 还没开始 |
