# issue 交付需求

这份文档管 issue 交付这个插件：一件改代码的活，车间的各个阶段怎么填。阶段和关口本身见 [核心.md](核心.md)；怎么做见设计文档（还没写）；用词以 [GLOSSARY.md](../../GLOSSARY.md) 为准。每条都经 Kun 认过，改之前先问他。

## 要的结果

你说一句要改什么，车间就把它交付到生产，DoD 全过；你只在 [介入点.md](介入点.md) 列的介入点出现。

不归这里：

- 阶段、关口、等待、失败处理这些所有活都有的，归核心。
- grant-console 的业务，以及它自己的授权卡怎么批，不归车间管。
- 有别人在用的交付对象，上线前要不要先批，以后接进来时再定。

## 要求

### 什么算「说一句」

**R1 你在协调对话里说要改什么，或者直接在 GitHub 开 issue，都会变成车间里的一件活；什么时候开工由车间按优先级安排（见 [介入点.md](介入点.md) R2–R4）。**
为什么：11-16 改：原来还有飞书群和「打上 `Ready for Agent`」放行；Kun「暂时不和飞书群交互」「应该要有个机制自动管理，我最多设置一下优先级」。

**R2 你打开这件活的 issue，看得到你的原话、DoD、能跑的检查，以及不可逆或对外的动作；要你亲眼看的，在这里写明在哪看、怎么送到你面前、你怎么回。缺 DoD 或能跑的检查的，车间不接单（核心 R2）。**
为什么：执行者一轮从头做到尾，进交付时照这里的 DoD 检查（R6）；写不清楚，查了也不算数。

**R10 issue 写明它落在哪几条需求上；要新增或改动需求的，以你在协调对话里的原话为确认，没有原话的车间不接单（见 [介入点.md](介入点.md) R2、R3）；合并时同一个 PR 改需求文档。**
为什么：Kun 11-13 担心 issue 没有规范导致项目行为漂移，同意增加「依据」节与需求变更确认（原话「2 加」，见 issue #52）。11-16 改：原来先发卡问你；需求变更卡看不懂（#129），Kun「需求目前都是在聊天里做对话梳理的，我想不出需要卡的地方」。

**R12 issue 之间的关系以 GitHub 上设的为准：blocked by 是前置，parent 和 sub-issue 是总单和子单，relates to 是相关。你在 GitHub 上改了关系，车间跟着改。总单按自己的正文和检查执行，子单只挡验收，不挡执行；子单全关后才进总单验收。**

### 什么算交付到生产

**R3 只有你自己在用的交付对象（grant-console、车间自己），检查和 CI 过了就合并，不等你；两者的上线都交给定时发版流程（见 [定时发版.md](定时发版.md)）。车间自己合并就算交付；grant-console 需要上线的改动，等包含该合并提交的一版上线后才算交付；只含规则配置的文档、测试或 Markdown 路径的活，按 R4 合并即交付。上线按定时发版 R6 申请指定应用和版本的代执行授权，例外的集群权限需说明具体必要性。**
为什么：你对 grant-console 说过「这个东西目前只有我自己在用啊，就直接上线就行了」（grant-console 项目经理的项目记录）。车间自己合并不等上线：Kun 11-14「目前可以宽松一些，逐渐把检查补上来」；要看上线后效果的活，在 issue 里写亲眼看（R7）。

**R4 只改文档、本机脚本、不用发版的活，合并完就算交付。grant-console 用唯一规则中的路径配置判断文档、测试和 Markdown 变更，重命名两端都要符合；混有服务变更仍等上线。**
11-15 返工确认依据同定时发版 R6；路径枚举不足或读取失败，不能当作无需上线。

**R5 issue 关上，就说明这件活 DoD 全过、已经交付；合并不会把它关掉。**
为什么：grant-console 的 #30 被合并自动关掉，跳过了验收卡（grant-console 项目经理的项目记录）。

### 什么算做完

**R12 执行从开始写代码到 PR 去掉 Draft，由一个执行者一轮做完；去掉 Draft 就是交接，不靠回执里的推进字段。合并、上线和上线后核对是交付，由程序做；等授权、等同步也由程序等，不起模型轮。**
DoD 检查不过，程序把 PR 改回 Draft，带原样输出退回执行；退回次数沿用规则里的上限，超了记卡住。上线后才测得出的项写在 issue 的「上线后核对」，交付时由程序跑，不算 DoD。grant-console 的发版手册还没写成程序前，上线照手册由执行者做，等待交给程序。
为什么：#164 放行到收尾 9 小时，执行者干活 46 分钟；说清楚、证据、交付、收尾各起模型轮，白跑 6 轮（复盘 20261116_B_ws164）。Kun 11-16「不用另外的模型做验收，检查就是防假做完，最后要提供DoD，才算完成；对于写代码来说，从开始写到PR去掉Draft这一步，就是执行的内容 后续的合并以及上线，是交付了」「进交付就要检查DoD啊」

**R6 DoD 由程序在进交付时检查：在干净副本重跑能跑的检查，核对每项 DoD 都有原样证据。不另派一家模型验收；过了就交付、收尾，不通知你。**
11-16 改：原来交付后由另一个 agent 照验收步骤验，Kun 原话见 R12。
为什么：grant-console 11-12 到 11-13 发了 7 张验收卡（Q1828、Q1829、Q1831 到 Q1835），你全部点了通过，没有一次退回；其中 Q1831 到 Q1833 在 08:34:56 到 08:35:01 发出，你在 08:35:55 到 08:36:02 之间连着点完。真正照步骤验的是项目经理，卡只是在确认它验过的结果（ask-kun 的提问记录）。

**R7 只有 issue 写明要你亲眼看的（界面、体验、文案这类检查跑不出来的），交付后才照 issue 写的方式送到你面前（见 [介入点.md](介入点.md) R9）。**

**R8 你随时在这件活的 issue 下回一句「不对」，那件活就退回执行，不管它是不是已经收尾。**
11-16 补：暂时不和飞书群交互，「不对」只认 issue 评论。
为什么：DoD 交给检查以后，漏掉的问题要等你用的时候才会发现，得有一条一句话就能退回的路。

### 什么算「你只在这些时候出现」

**R9 写代码、审查、修必须改、合并、上线，都不问你；碰到不可逆、对外、花钱的，按核心的 R3 在授权中心申请。**
为什么：你 11-12 对 grant-console 说过，项目经理「不应该在那边提问题等我看到再回答他，因为我很有可能一个月都不会打开这个页面」（grant-console 项目经理的项目记录）。

**R11 车间程序及执行者在 GitHub 上的动作使用交付对象规则指定的身份。kun-g/workshop 使用 lambdatheory-agent App；kun-g 只代表 Kun 本人亲手进行的动作。grant-console 暂时保持现有身份及批准方式。需要 GitHub 动作的执行轮和程序作业按目标仓库取得 App 令牌，只传给执行动作的进程，不把令牌写入日志或事实，不修改全局身份配置；签发失败时不执行该轮或动作、不回退到个人身份，记录原因，记成卡住，由项目经理处理（见 [介入点.md](介入点.md) R11）。审查和验收仍遵守现有只读凭据隔离。GitHub 来源接单只认两种 issue：kun-g 本人开的，和协调对话用 App 身份开、正文写明 Kun 原话和会话号的；开单身份回源核实，正文其余文字只当资料。返工评论只认 kun-g 本人的，bot 动作不触发返工。Kun 在会话里的回答，由协调对话用 workshop 命令登记，带上原话和会话号，效果等同 Kun 本人操作；原话和会话号必填且不得为空白，事实记录 channel=session、会话号及原话，why 可查看。**
为什么：Kun 11-13「所有Agent做的行为都用APP自己来做。」；11-14 对会话放行与 GitHub 身份分离方案回答「按推荐」，见 issue #31。11-16 改：不再要放行标签（[介入点.md](介入点.md) R2–R4），签发失败不再通知（[介入点.md](介入点.md) R13）。
