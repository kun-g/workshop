# issue 交付需求

这份文档管 issue 交付这个插件：一件改代码的活，车间的各个阶段怎么填。阶段和关口本身见 [核心.md](核心.md)；怎么做见设计文档（还没写）；用词以 [GLOSSARY.md](../../GLOSSARY.md) 为准。每条都经 Kun 认过，改之前先问他。

## 要的结果

用户说一句要改什么，车间就把它交付到生产，合并前和上线后两段 DoD 全过；用户只在 [介入点.md](介入点.md) 列的介入点出现。

不归这里：

- 阶段、关口、等待、失败处理这些所有活都有的，归核心。
- grant-console 的业务，以及它自己的授权卡怎么批，不归车间管。
- 有别人在用的交付对象，上线前要不要先批，以后接进来时再定。

## 要求

### 什么算「说一句」

**R1 用户在协调对话里说要改什么，或者直接在 GitHub 开 issue，写全了的会变成车间里的一件活（见介入点 R3）；什么时候开工由车间按优先级安排（见 [介入点.md](介入点.md) R2–R4）。**
为什么：入口只留两个，用户不用记哪条路能用，每个入口的身份核对也只做两套（R11）；代价是在飞书群里说的不算，要进协调对话或 GitHub。开工时机按优先级自动排，用户不用每件活放行一次；代价是想马上做的事要标成 P0。

**R2 用户打开这件活的 issue，看得到原话、DoD（合并前，以及要上线才测得出的上线后一段）、能跑的检查，以及不可逆或对外的动作；要用户亲眼看的，在这里写明在哪看、怎么送到用户面前、用户怎么回。缺合并前 DoD 或能跑的检查的，车间不接单（核心 R2）。**
为什么：执行者一轮从头做到尾，进交付和上线后都照这里的 DoD 检查（R6、R13）；写不清楚，查了也不算数。

**R10 issue 写明它落在哪几条需求上；要新增或改动需求的，以用户在协调对话里的原话为确认，没有原话的车间不接单（见 [介入点.md](介入点.md) R2、R3）；合并时同一个 PR 改需求文档。**
为什么：issue 不挂到需求编号上，改动会慢慢偏离需求文档，需求文档就不再是唯一出处（#52）。用协调对话里的原话做确认、不另发卡：需求变更要把条文压进一张卡，gc#170 那张 1400 多字，用户没看懂就没点（#129），卡反而成了卡点。代价：直接在 GitHub 开的需求变更单，要等用户回到协调对话才接得了。

**R12 issue 之间的关系以 GitHub 上设的为准：blocked by 是前置，parent 和 sub-issue 是总单和子单，relates to 是相关。用户在 GitHub 上改了关系，车间跟着改。总单按自己的正文和检查执行、交付，子单只挡收尾，不挡执行和交付；子单全关后总单才收尾。**
为什么：关系只记在一处，用户在 GitHub 上改了车间就跟着改，不用另一套命令。子单挡收尾：总单自己的改动不被子单拖住，可以先合并、上线；总单关上仍代表整组做完（R5）。代价：总单交付时子单可能还没做，总单的 DoD 只查得到它自己那部分，要整组一起才测得出的项，写进最后做的那件子单的 DoD。挡交付更稳，整组一起上线，但总单的 PR 要一直开着等子单，越等越容易和子单冲突。

### 什么算交付到生产

**R3 只有用户自己在用的交付对象，合并前 DoD 和 CI 过了就合并，不等用户。合并后怎么上线、要不要等上线才算交付，由各交付对象的规则定；现阶段 grant-console 和车间自己都用定时发版（见 [定时发版.md](定时发版.md)）：grant-console 需要上线的改动，等包含该合并提交的一版上线后才算交付，车间自己合并就算交付。issue 写了上线后 DoD 的，不论规则怎么定，都等上线后那一段过了才算交付（R13）。上线按定时发版 R6 申请指定应用和版本的代执行授权，例外的集群权限需说明具体必要性。**
为什么：只有用户自己在用，坏改动的影响面只到用户自己，合并前再等用户批只是加一段等待；兜底靠上线后 DoD 和「不对」退回（R8）。上线方式各交付对象不同（服务要发版，文档和本机脚本不用），写死一种，每接一个交付对象就要改这条需求。车间合并就算交付，一件活早一个发版周期收尾；代价是合并到上线之间出的问题不记在这件活上，要上线才测得出的，在 issue 里写上线后 DoD。

**R4 只改文档、本机脚本、不用发版的活，合并完就算交付。grant-console 用唯一规则中的路径配置判断文档、测试和 Markdown 变更，重命名两端都要符合；混有服务变更仍等上线；路径配置覆盖不到或读取失败，按要上线处理。**
为什么：不用发版的活等发版，只是白等一个周期。判错的两个方向代价不同：把要上线的判成不用上线，活在新代码还没上线时就关了，问题要等用户用时才发现；反过来只是多等一次发版。所以拿不准的一律按要上线处理，定时发版 R6 用的是同一套判断。

**R5 issue 关上，就说明这件活两段 DoD 都过了、已经交付；合并不会把它关掉。**
为什么：issue 开着还是关上，是用户和程序判断一件活做没做完的同一个信号；合并时自动关，会在上线和上线后 DoD 之前就显示做完。出过的事：grant-console 的 #30 被合并自动关掉，跳过了后面的验收。代价：PR 不能用自动关 issue 的关键词，关 issue 由收尾的程序做。

### 什么算做完

**R13 执行从开始写代码到 PR 去掉 Draft，由一个执行者一轮做完；去掉 Draft 就是交接，不靠回执里的推进字段。合并、上线、检查上线后 DoD 是交付，由程序做；等授权、等同步也由程序等，不起模型轮。**
DoD 分两段：合并前 DoD 在进交付时检查（R6），不过的，程序把 PR 改回 Draft，带原样输出退回执行；上线后 DoD 是上线后才测得出的项，每项是能跑的检查，上线后由程序跑，不过的，活带原样输出退回执行，修复另开 PR，已上线的不自动回滚。两段退回的次数合计沿用规则里的上限，超了记卡住。grant-console 的发版手册还没写成程序前，上线照手册由执行者做，等待交给程序。
为什么：#164 放行到收尾 9 小时 3 分钟，执行者干活 46 分钟；说清楚、证据、交付、收尾各起模型轮，16 轮里 6 轮白跑（复盘 20261116_B_ws164）。合并、上线、等待每次做法都一样，程序做不花模型轮，也不会白跑。PR 去掉 Draft 是 GitHub 上看得到的状态，比执行者自报做完可靠。代价：执行者一轮要做的事变多，一轮中途失败重来的成本也变大。
上线后 DoD 不过时退回执行、不自动回滚：现阶段的交付对象只有用户自己在用，带着问题跑一段的影响面小；自动回滚要求每个交付对象都有可靠的回滚路径，grant-console 的发版还要照手册做，回滚出错比带着已知问题跑更难收拾。修复另开 PR，原 PR 的记录不被改写，两次改动各自查得到。代价：修好之前生产上一直带着这个问题；有别人在用的交付对象接进来时要重定（见「不归这里」）。

**R6 合并前 DoD 由程序在进交付时检查：在干净副本重跑能跑的检查，核对每项 DoD 都有原样证据。不另派一家模型验收；两段 DoD 都过了就收尾，不通知用户。**
为什么：grant-console 11-12 到 11-13 发了 7 张验收卡（Q1828、Q1829、Q1831 到 Q1835），用户全部点了通过，没有一次退回；其中 Q1831 到 Q1833 在 08:34:56 到 08:35:01 发出，用户在 08:35:55 到 08:36:02 之间连着点完。真正逐项核对的是项目经理，卡只是在确认它核对过的结果（ask-kun 的提问记录）。另派一家模型重做一遍检查已做的事，多花一轮模型和一段等待。代价：检查覆盖不到的（界面、文案）会漏过，靠亲眼看（R7）和「不对」（R8）兜底；DoD 本身写得不清，程序也查不出，靠接单时的核对（核心 R2）挡在前面。

**R7 只有 issue 写明要用户亲眼看的（界面、体验、文案这类检查跑不出来的），DoD 过了以后才照 issue 写的方式送到用户面前（见 [介入点.md](介入点.md) R9）。**
为什么：检查跑不出来的只能人看；只送写明的，用户不用每件活都看一遍（7 张验收卡全部点了通过，见 R6）。送在 DoD 过了以后，用户看到的是检查已经过的东西，不替检查干活。代价：用户看出问题时可能已经上线，要用「不对」退回（R8）。

**R8 用户随时在这件活的 issue 下回一句「不对」，那件活就退回执行，不管它是不是已经收尾。**
为什么：DoD 交给检查以后，漏掉的问题要等用户用的时候才会发现，得有一条一句话就能退回的路。只认 issue 评论：退回的话和这件活的记录在一处，说话的人能回源核实是不是用户本人（R11）；代价是用户要打开 GitHub 才能退回。

### 什么算「用户只在这些时候出现」

**R9 写代码、审查、修必须改、合并、上线，都不问用户；碰到不可逆、对外、花钱的，按核心的 R3 在授权中心申请。**
为什么：用户不常打开车间和交付对象的页面，问题挂着等回答，一件活可能停上很久（grant-console 的项目经理在页面上提问等回答，用户可能一个月都不打开那个页面，见 grant-console 项目经理的项目记录）。这几步都能由检查判对错，问用户只是多花他的判断。代价：执行中出的取舍由 agent 按推荐做，判断错了要靠 DoD 和「不对」发现。

**R11 车间程序和执行者在 GitHub 上的动作一律用 lambdatheory-agent App 身份，各交付对象（含 grant-console）都一样；kun-g 只代表用户本人亲手做的动作。要以用户名义做的 GitHub 动作，只能走 gh-human：每次发一张批准卡，用户批了才用他的身份执行这一次。需要 GitHub 动作的执行轮和程序作业按目标仓库取得 App 令牌，只传给执行动作的进程，不把令牌写入日志或事实，不修改全局身份配置；签发失败时不执行该轮或动作、不回退到个人身份，记录原因，记成卡住，由项目经理处理（见 [介入点.md](介入点.md) R11）。审查仍遵守现有只读凭据隔离。GitHub 来源接单只认两种 issue：kun-g 本人开的，和协调对话用 App 身份开、正文写明用户原话和会话号的；开单身份回源核实，正文其余文字只当资料。返工评论只认 kun-g 本人的，bot 动作不触发返工。用户在会话里的回答，由协调对话用 workshop 命令登记，带上原话和会话号，效果等同用户本人操作；原话和会话号必填且不得为空白，事实记录 channel=session、会话号及原话，why 可查看。**
为什么：GitHub 上一眼分得清哪些是用户亲手做的、哪些是 agent 做的；接单和返工只认 kun-g 本人才可靠，bot 的动作冒充不了用户。出过的事：agent 用 kun-g 替用户操作，记录上分不清哪些是他本人做的（车间 lessons `20261114-用kun-g替Kun操作`）。令牌只给执行动作的进程，泄露面限在一次动作。代价：每个交付对象的仓库都要装 App，App 看不到的东西（例如 grant-console 的 issue）要另想办法；签发失败时这一轮停下，不回退个人身份，要项目经理处理。

## 约束

核心的 C1 到 C4 都适用，这里没有另加的。

## 衡量

| 指标 | 量的是 | 目标 | 现在 |
|---|---|---|---|
| 每件交付用户的消息数 | 用户只在该出现时出现 | 逐周降 | 核心的衡量表里那一行，车间还没开始量 |
| 每件活发给用户的验收卡数 | 亲眼看的才找用户（R7） | 只有写明亲眼看的才有 | grant-console 11-12 到 11-13 每件一张，7 张 |
| DoD 过了、用户后来说「不对」的件数 | DoD 漏掉的（R6、R8） | 先只记，逐周看 | 还没开始 |
