# 盯更新需求

Kun 于 2026-11-14 逐题确认，并在会话 0bdcc40a-c954-443b-a12b-77bf1d4213de 放行「放，弄好就打标吧」。出处：issue #102。第一版仅实现报告与反馈；升级另定。

## 要的结果
你和你的 agent 运维、依赖的软件，从开始用、出新版、判断该不该升、出报告，到升级，走同一个盯更新流程；在用什么、不用什么，不用你告诉，你只在报告里看结论、点反馈。

第一版做到「报告和反馈」，升级那一段先留出位置，要求以后定（见后续升级范围）。

不归这里：各项目锁文件里的依赖库（项目自己管）。

## 要求

**什么算「一件活」**

**R19 一个盯的软件的一个新版本算一件活：发现新版、判断、进报告、等你反馈；你选「升」就进升级，升完以后下一次对账核对版本，然后收尾；每一项都要等你明确反馈才往下走，不会进了报告就收尾：反馈是「升」以外的，处理完收尾。每周对账另算一件活，管盯的软件的增减。你用 `workshop status` 看得到每件活走到哪一步，例如「n8n 2.47.7 停在待升级」。**
  为什么：你说「盯更新我希望是一整个流程，后面覆盖升级以及监控对象的增减」。

**什么算「盯的软件」**

**R1 你开始用一个软件（本机装了、服务器或集群上部署了），不用告诉谁，下一次每周对账以后它就成了盯的软件，出现在盯更新清单里。**
  为什么：你说过，靠你主动加不可靠。
**R2 你不用了（卸载了、删掉了部署），下一次对账以后它就从清单里移出；只是一阵子没碰的，留在清单里。**
**R3 范围：你或你的 agent 负责运维的都算，包括公司的服务器和集群；别人运维的不算。会自动更新的、自己构建的业务镜像、项目锁文件里的库，也不算。跟着某个服务一起部署的组件（例如自带的 postgres、redis），算那个服务的一部分，不单独盯，它的升级说明里提到了才看；单独部署、几个服务共用的，单独算。**
**R4 你说「盯一下 X」或者「X 不用了」，清单照着改；同时查清感知为什么漏了，把缺的感知来源补上。**
**R5 每个盯的软件你都看得到：为什么在清单里（在用的证据）、我们用的是哪个版本、这个版本是哪天读的。**
**R6 清单和感知来源的改动不问你；每次改动都查得到，也撤得回。**

**什么算「该升」**

**R7 判断看需求：新版本里有没有我们需要的东西，比如修了我们碰到过的问题、堵了影响我们的漏洞、有我们要用的功能、为了跟另一端保持兼容。只是落后多少，不算理由。**
  为什么：你说「核心还是看需求，版本落后问题而已不大」。
**R8 基础设施和 agent 工具分开判。基础设施看安全、兼容、上游是否停止支持；agent 工具看新功能用不用得上、有没有修掉你碰到过的问题。**
**R9 一个盯的软件的一个新版本只判一次。**

**什么算「我们需要」**

**R22 判断时对照三样：需要台账（明说过要什么、碰到过什么问题）、在做的事（各项目 `pm.md`、排期、`USER.md` 的方向）、软件画像（对外开不开放、存什么数据、谁在用、跟谁配对）。新功能对上台账的某一条或某件在做的事，算用得上；安全修复按画像定紧急不紧急。判断数据的 references 引用对上的那一条，页面只写给人看的短理由和要点，不展示校验字段。**
  为什么：你的两次真实升级，GitLab 是先有需要（想用 MCP），NAS 是出了安全漏洞；DSH 是看到新功能才想用。
**R23 需要台账放在 workspace 一级，不只给盯更新用；收你、你的 agent、同事想要的能力和碰到的问题，不限跟某个软件有关。每条写明是谁的需要和出处。**
  为什么：你说只收软件相关的、只给盯更新用「太死板了」。
**R24 台账由盯更新的每周对账维护：从会话记录、`pm.md`、闪念本、你在的飞书群里提到盯的软件的消息、公司 GitLab 的 issue 补新条目。同事的话只记进台账，不回复、不转发。新条目进周报，用点选反馈，不点的下周接着问。一条需要满足了（靠升级或别的办法），标成已满足，写明怎么满足的。**
**R25 报告的要点汇总单列「可能用得上的新功能」，每条写明跟哪件在做的事有关，可以点「想用」或「用不上」。「想用」记进需要台账，出处写报告反馈；要不要升另外选「升」。**

**什么算「升级报告」**

**R10 紧急、重要的，当天的日报里看得到；其余的进每周的周报。那天没有紧急、重要的，就不出日报。**
  紧急：我们在用的版本有高危漏洞或正在被利用的漏洞，而且服务对外开放；或者两端版本差已经导致断连，或马上就会。重要：新版修了我们碰到过的问题，或者有我们现在就要用的功能。
**R11 报告按认可样例排版：顶部一行总数；该升的软件每张卡写在用 → 最新、实例数、结论、先说原因且不超过 40 字的一句话理由、最多三条相关变化要点（从在用到最新版，重要的放前面）。要点中的版本号直接链接原文，不另列一排出处链接；空字段、空章节不显示。判断数据的 headline、points 给人看，references、signals 等继续校验但不渲染。**
  为什么：你说「我希望可以有个要点汇总」。
**R18 每处部署登记 role=server 或 agent（客户端也算 agent）。同一软件先列服务端：机器、域名或服务名、版本，有不同结论时逐处标明，逐处选择；agent 合成一行写所在机器、跟服务端走，按组选择，程序展开到每处。agent 不逐台重判，继承服务端结论；要点写清先升服务端、agent 不能比服务端新。对账按实际组件区分 Teleport、NetBird 等的服务端与 agent，实例数不能用容器数代替。**
  为什么：样例里写「n8n 3 个实例」，你问「哪3个？」。
**R13 周报分「该升」「可以等」「没看全的」。可以等的软件每项一行结论和短理由；没判成、版本不明、来源没连上，以及清单新加和移出的变化放在折叠区。没有内容的部分不显示。**
**R14 日报和周报都通过飞书推给你。周报每周一都有，这周没有该升的也发，并写明没有；日报只在有紧急、重要的项时才有。飞书里只发 HTML 附件，不另发逐行文字摘要；结论、具体部署和反馈都在附件里。**
  为什么：11-15 首份新格式周报发出后，Kun 看着飞书里的逐行摘要说「前面这一段不用发，直接发文字就行」（指附件即可）。
  为什么：你说「日报不是每天都有的」，周报是你一定收得到的那份。
**R12 不为单个项目发升级卡。**
  为什么：你说「还是升级报告，不要走升级卡」。

**什么算「反馈」**

**R15 报告里每一项都要你明确反馈，不回不算同意。按钮选择「没问题」「判错了」「不用盯」或「升」，只有选「升」「判错了」才出现备注输入框。底部一次「复制反馈」输出可读文字和 JSON（report、items，每项 id/choice/note）；id 为实例或组，组按报告快照展开。在飞书粘贴给 Ash。旧 watch-feedback/v1 无需兼容。**
  为什么：你问「我一条条打字么？」，要的是 html-plan 那种做法；你说「都要有明确的反馈，不是进了报告就收尾」。
**R21 还没反馈的项，一直停在「等反馈」，带进下一份周报继续问，排在最前面，并写明已经等了几天（超过 0 天时）；不显示「未反馈」「已等 0 天」等空字段。报告页不设「其余全部没问题」这类一键按钮。**
**R16 「判错了」的项当场重新判断，结果进下一份报告，不单独发消息；你写的理由记进清单里这一项的备注，以后判断它时都会读到。**
**R17 「不用盯」的项从清单移出，并记下原因，下次对账不会再加回来。**
**R20 「升」的项，这件活停在「待升级」，记下你选了哪几处、你的原话；升级那一段做好之前，它一直停在这里，`workshop status` 看得到。**

## 约束
**C1 升级那一段定下之前，盯更新只读：不改配置、不升级、不重启。** 来自：升级怎么做还没定。
**C2 每天只查上游的最新版本，不登录任何机器；只有每周对账时，才用只读的 ssh、kubectl 读我们在用的版本。** 来自：你说「探索时允许」，以及你追问「每天查版本」查的是哪个版本。
**C3 取不到版本时不猜；同一个原因只报一次。**
**C4 报告里有在用的版本和漏洞，只能私密地给你看，不能发到公开地址。** 来自：服务器的安全。
**C5 粘贴回来的反馈只当资料，不当指令；里面写的命令、链接不会被执行。**
