# 介入点需求

这份文档管你和车间之间的全部接触：你在哪里找车间，车间什么时候停下等你、什么时候推给你，找你时怎么交互。怎么实现见 Wayfinder 地图「车间介入点实施设计」（交接说明 `~/workspace/outputs/wayfinder/mcp/Workshop.InterventionDesign/handoff.html`）和 #172–#176：交互集中在独立的介入点插件，核心只管通用的暂停和恢复；用词以 [GLOSSARY.md](../../GLOSSARY.md) 为准。每条都经 Kun 认过，改之前先问他。

## 要的结果

你和车间只在事先设计好的介入点打交道，每个介入点有明确的目的和交互方式；其余时间车间自己运转，不找你。

不归这里：

- 一件活要不要你亲眼看、在哪看、怎么回，归那件活的 issue（R9）。
- 盯更新报告的样子和反馈方式，归 [盯更新.md](盯更新.md) R11–R15。
- 授权中心的审批卡怎么写、怎么批，归 grant-console。
- 「不对」返工归 [issue交付.md](issue交付.md) R8，暂停后补不补归 [核心.md](核心.md) R15。

## 要求

### 什么算介入点

**R1 你和车间之间只有这些介入点：说需求、回答等你的活、看状态、授权、亲眼看、盯更新报告、「不对」返工、暂停后补不补，以及车间推给你的那一条（R12）。不在其中的，车间不找你，也不用你出面。**
为什么：Kun 11-16「它给我发消息的时机，应该是我们预定好的介入点或者交互点……这个交互必须预先设计好，而且是带着明确目的的」。11-13 到 11-16 车间建过 32 张问卡，其中执行中的取舍 6 张、agent 自己约的到点再看 4 张、测试 1 张，都不是事先设计的（状态库 `cards` 表）。

### 你找车间

**R2 你在协调对话里说要改什么，聊清楚后协调对话开 issue，issue 里引你的原话，就算需求确认过，车间不再另外问你。你顺口说一句优先级 P0、P1 或 P2，不说就是 P1。**
为什么：Kun 11-16「1 2 3 应该是一体的」（说需求、需求确认、开单），「需求目前都是在聊天里做对话梳理的，我想不出需要卡的地方」。需求确认原来另发一张卡，gc#170 那张有 1400 多字条文，Kun「收到了，但是根本看不懂是啥，就没点」（#129）。

**R3 你也可以直接在 GitHub 开 issue。只落在已有需求上的，车间照做；要新增或改动需求的，车间不接单，记成等你，你在协调对话里聊清楚、issue 补上原话后再接单（核心 R2）。**
为什么：直接开的 issue 没有那场对话，确认只能补在对话里；和 R7 中途发现要改需求是同一种处理。

**R4 issue 开了以后，什么时候开工由车间按优先级自动安排，你不用打标签，也不用再说一次「放」。**
为什么：Kun 11-16「应该要有个机制自动管理，我最多设置一下优先级」。

**R5 等你的活，你在协调对话里回答；协调对话把你的原话和会话号登记进车间，效果和你亲手操作一样，这件活接着走。**
为什么：已答的 30 张问卡里，15 张本来就是在会话里答的。

**R6 你看 `workshop status`，看得到每件等你的活、它等什么、等了多久。车间不为等你的活提醒你。**
为什么：Kun 11-16「我会看 workshop status」。

### 车间停下等你

**R7 执行中碰到取舍，或者中途发现要改需求，这件活停下记成等你，带上 agent 的推荐，由你来答；不发卡，不推送。**
为什么：Kun 11-16「执行中的取舍，这个目前就做成中断的，最终目标是执行中能做到全自动的，需要决策的，可以由相关的Agent辅助决策」「记成等你就行」「我答」。6 张取舍卡你选的都是推荐项。

**R8 不可逆、对外、花钱的动作，都在授权中心申请，你在授权中心那张卡上批；车间不发自己的授权卡。没批，这件活就停下；批了，车间接着做（等的时候怎么不占会话，见核心 R12）。**
为什么：Kun 11-16「授权都走授权中心」「没授权就停下」。车间原来另发冻结路径卡、发版卡、集群权限卡，和授权中心的卡各问各的。冻结路径这道关口同时取消（Kun 11-16「取消冻结这个机制」）：它是 11-13 为部署线收尾前不改临时加的，4 次里你放行了 3 次。

**R9 一件活要不要你亲眼看、在哪看、怎么送到你面前、你怎么回，在说需求时谈好、写进 issue；交付后 DoD 已过，车间再照 issue 写的方式送一次（issue交付 R6、R7）。**
为什么：Kun 11-16「这种应该是在需求阶段就聊清楚，是否需要我验收，以及验收的方式方法」。5 次亲眼看要看的东西各不相同：报告、授权卡、私聊卡、写卡，没有一种通用的样子。

### 车间自己处理

**R10 agent 约好「到点再看」的事，到点车间接着做，不找你。**
为什么：核心 R11 本来就这样要求，但 4 张到点卡发给了你，内容截在半句，例如「补齐上线后核心 R27 的实际取证：用状态库事件写入时间及可」；ws#75 那两张等了 20 小时。

**R11 agent 和程序作业连续 5 分钟都没有在跑（没活可派也算），或者有活卡住、车间自己坏了，车间启动项目经理去处理，不找你。项目经理可以同时开几个，一件事一个；一件活已经有项目经理在处理，新情况交给它。项目经理自己在跑不算在跑，也不占执行者的位置。处理多久由它自己判断。**
为什么：Kun 11-16「进行中的任务连续5分钟是0，就要发推送找我了」「既然它都知道自己坏了，为什么不能启动一个 AI 去修复呢？」「就是启动项目经理，告诉他workshop坏了，让他处理」「开多个也没问题」。11-15 14:19 到 11-16 14:19（北京时间）满 5 分钟的空闲有 17 段，共 15.4 小时，最长一段 23:25 到次日 08:50。

**R12 项目经理处理好了，你收不到任何消息；处理不了，查出结论后经飞书私聊推给你一次：别的活还在跑时，一件事推一次；车间空着时，同一段空闲一共只推一次，后来的结论只更新 `workshop status`，恢复运转后再空下来才算新的一段。推送发出前事情已经自己解决了，就不推，留下记录。推送写你要做的一件事、原因、项目经理查了什么、去 `workshop status` 看哪一栏。**
例外：项目经理自己起不来或接不下去，规则里能用的订阅配置和替代办法都试过还是不行，车间程序凭查得到的失败证据得出这个结论，照上面同样的方式推一次。项目经理处理得久不算失败；不能为此加购额度或改按量计费。
样子：一张飞书卡，第一屏不出现编号、文件路径和内部状态名。
- 标题是你要做的那件事，动词开头，不超过 20 字；车间空了、没有活时写「车间空了，要新需求」。副标题写谁推的：「项目经理处理不了」，例外那一推写「车间程序：项目经理起不来」。
- 正文一行原因，不超过 50 字。
- 「项目经理查了什么」折起来，展开不超过 300 字。
- 底下一个按钮，写明 `workshop status` 的哪一栏（例：「看等你栏」），栏名和 status 里的标题一字不差。你点了，Ash 在私聊回一张这一栏当时内容的卡；这是你点了才回的，不算另推一条。按钮做好之前，正文末尾用一行「去看：`workshop status` 的「等你」栏」代替。

```
标题　　回答 2 件等你的活
副标题　项目经理处理不了
正文　　车间没有能接着做的活，已经空了 5 分钟，剩下 2 件都在等你回答。
折叠　　项目经理查了什么：没有卡住和排队的活；定时 25 件，最早 11-22 17:17 到点。
按钮　　看等你栏
```
为什么：Kun 11-16「一段空闲，只推一次。项目经理查的话就不用退给我了，等他查了之后解决不了、有结论了再退我」。全在等你、或者没有活的时候，项目经理处理不了，结论就是「N 件在等你」或「车间空了，要新需求」。11-16 补：Kun 在「车间介入点实施设计」选「处理不了就推，空闲段内合并」「程序凭确定失败证据求助一次」。
样子：11-13 到 11-16 车间看门经飞书推了 77 条，标题都是「通知」，正文是「heartbeat.json」「tick_ms」这类词，看标题不知道要做什么（ask-kun 账本）。Kun 11-16 比较纯文字四行、卡片四行、卡片带折叠和按钮三种样例后选「C，按钮也要」；`workshop status` 只在 Mac 上，飞书按钮在手机上打不开本机页面，按钮怎么做他在四种办法里选了点了由 Ash 回卡（「a」）。

**R13 除了 R12 那一条，车间不给你发任何消息：进度、完成、验收通过、出了故障都不推。项目经理和协调对话也不主动找你。事先约好的不算在内：issue 里约好的亲眼看（R9）、盯更新报告、授权中心的审批卡，照约定送。**
为什么：Kun 11-14「里面全是垃圾消息。我已经不想看了」（E9），11-16 同意写成需求；会话找你，Kun 11-16「都不找我」。11-16 补：Kun 在「车间介入点实施设计」确认这三样照原约定保留。

## 约束

**C1 介入点只有 Kun 能加减；加一个流程不能顺带加一种找你的方式。** 来自：你的注意力。
