# 核心需求

这份文档管车间的核心：事件进来变成一件活，活按阶段走到收尾，阶段之间有关口；每一类活怎么填各个阶段，归它的插件。怎么做见设计文档（还没写）；用词以 [GLOSSARY.md](../../GLOSSARY.md) 为准。每条都经 Kun 认过，改之前先问他。

## 要的结果

核心让车间这套自动运转的交付体系转起来：服务于整个系统的目标，让整个系统易于扩展，各部分之间低耦合。

整个系统的目标沿用操作系统目标的第 3、4、1 条：各线自己往后推；同样的结果，Kun 的判断更少；有大局。

不归这里：

- 每一类活的各个阶段怎么做，归它的插件。第一个插件是 issue 交付，它的需求另写一份。
- 执行这一段里面怎么做，由执行者自己定。
- grant-console 是车间的交付对象之一；它自己的流程问题不归车间管，它那套临时循环的经验只当参考。
- 闸口和飞书一侧（收发信、卡片、Ash）是插件，各有自己的需求。

## 要求

### 什么算一件活走完

**R1 任何一类活，你都能说出它走到了哪个阶段。**
阶段是接单、说清楚、执行、证据、审查、交付、验收、收尾，加可选的观察。某类活用不到的阶段可以跳过，执行里面怎么做不规定。
为什么：软件 issue、视频、周报、调研、运维告警五类活现在的做法都能填进这组阶段，不同的只是每一格填什么（11-13 需求对齐页 v4 图 2）。Baton 和 flow-issue-to-prod 都把执行拆成过固定的小步，最后都并回了一步：Baton poc-v7 让接力退役，flow-issue-to-prod 把 8 个节点并成一个。

**R2 说清楚这一段没写出能跑的检查，活不开始执行。**
为什么：做完了没有，要靠检查的输出判，不靠 agent 自己说；「假做完」是 agent 不守规矩的五种样子之一（见 GLOSSARY.md「假做完」）。

**R3 交付里有不可逆或对外的动作，先经你批一次；你已经交给 agent 判断的那类，不问。**
例：一件活交付前要对外发消息，过关口时问你一次。
为什么：给别人发消息、付款、删别处的东西属于「只起草」一档（见 GLOSSARY.md）；已经放给 agent 的再问，就是多花你的判断。

**R4 验收不过，活回到执行，不算做完。**

**R5 一件活做完以收尾为准；任何一件活停下，都留下工序、送回或等你三样之一。**
为什么：登记与送回是操作系统的机制，停下不留这三样就会丢（见 GLOSSARY.md）。

### 什么算事件

**R6 让一件活开始或往下走的都算事件，包括你直接给 agent 发的消息。**
你在 Orca 里直接对一个写代码的会话说「这里换个做法」：这算那件活的一个事件，核心记下来，不改派，也不拦。
为什么：不记下来，R9 查一件活为什么这么跑就缺一块。

**R7 同一个东西上的事件归到同一件活；一件活同一时间只跑一轮，同时在跑的活数有上限。**
例：同一个 issue 上接连来了三条评论，你看到的是一件活往下走，不是三个会话同时在改。
为什么：grant-console 现在写死同时 2 个，其他系统各管各的（11-13 需求对齐页 v4 图 4）。

### 什么算服务于整个系统的目标

**R8 你问「现在都有什么活」，看到一张图：每件活在哪个阶段、谁在推、下一步是什么、卡在谁手里。**
为什么：这是操作系统目标第 1 条「有大局」的原话落到活上。

**R9 你问一件活为什么这么跑，一条命令看到它每一轮的起因和结果。**
为什么：现在 `~/.local/state` 下有二十多个账本目录，查一件事要翻好几处（11-13 需求对齐页 v4 图 4）。

**R10 你看得到每件活、每天和最近 7 天花了多少 token 和钱。**
为什么：ai_quota 只看订阅额度，按轮的花费现在没处看。

**R11 agent 说「半小时后再看」，到点它自己接着干，你不用提醒。**
为什么：现在每个系统各写一份等待和轮询。

**R12 一件活等你回答时不占着会话、不花 token；你答了，它接着原来那件活往下走。**
为什么：Orca 会话现在开着等。

**R13 一轮跑完，它要你的、通知你的、约好再看的时间，都记进核心，不只写在会话的文字里。**
为什么：收尾句和交接现在是文字约定，盯梢要靠读文字认。

**R14 一件活反复跑不成，你只收到一次通知，它不会一直重试下去。**
为什么：现在是盯梢加各系统各自处理失败。

**R15 你可以让某一类活暂停；恢复时列出暂停期间漏掉的事件，由你定补不补。**
为什么：grant-console 的 `dispatch_paused.json` 这类开关，现在各写各的。

**R16 什么活交给谁、在哪个目录、用哪个 skill、什么权限、哪几类事先问你，都写在一份规则里，你只看这一处。**
为什么：现在散在自动派活的章程、接线台的分诊规则和 grant-console 的代码里。

### 什么算易于扩展

**R17 加一类新活（比如每周的 Steam 选题信号），写一份规则加 skill，或写一个插件把各个阶段填上；核心不用改。**

**R18 换一个执行者（比如审核从 Grok 换成 Codex），只改规则里的一处，插件和核心都不动。**
为什么：额度用完、模型换代都会换执行者，每换一次都要改插件或核心，就谈不上易扩展。

**R19 接入一个新流程，这件活的观察阶段跑一条固定的检查：核心改了多少行，新流程的第一件活多久跑通。**
为什么：易于扩展在加新流程时评判，算在观察这一段；不放一条固定的检查，就不会有人去评。

### 什么算低耦合

**R20 一个插件出 bug 崩了，别的类的活照常跑；受影响的那几件标成卡住，告诉你一次。**

**R21 飞书断了，agent 照常干活；要你拍板的事不丢，飞书恢复后你看得到。**
为什么：接线台 11-06 Ash 的长连接断过约 20 分钟（接线台 11-06 的运行记录）。

**R22 你翻核心的代码，找不到 PR、视频、周报这类只属于某一类活的词；它只认事件、活、阶段、关口。**

### 坏了怎么办

**R23 车间自己停了或卡住，你不用去看就会知道，然后由你介入。**
为什么：车间也交付它自己，它坏了不能只靠它自己报。

## 约束

**C1 外部的文字（issue 正文、网页、别人发来的消息）只当资料交给 agent，不当指令。** 来自：安全。
为什么：交付对象不止 Kun 自己的仓库，外部文字谁都能写进来。

**C2 agent 发出的事件再派给 agent，连锁超过 8 层就停。** 来自：费用和运行稳定。
为什么：防止 agent 之间互相派活转圈；8 层沿用 autoloop。

**C3 车间按自己的情况写新代码；以前的轮子（Baton、flow-issue-to-prod、grant-console 的临时循环、接线台）只当参考，不搬代码。** 来自：以后好改。
为什么：Baton 1.25 万行里，真正把 issue 推到合并的约 2.4k 行，其余是流程库、评测、看板；flow-issue-to-prod 2.1 万行，交付到别的仓库 0 件（11-13 四套 issue 循环的对比）。

**C4 只用现有订阅和已经付过的额度；要加购额度或开按量计费，先问你。** 来自：花钱由 Kun 定。
为什么：车间自己会一直跑，每一轮都在花额度；grant-console 这个月 Cursor 第三方额度和 Grok CLI 额度都先后用完过（grant-console 负责会话的项目记录）。
