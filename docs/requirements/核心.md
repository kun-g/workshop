# 核心需求

这份文档管车间的核心：事件进来变成一件活，活按阶段走到收尾，阶段之间有关口；每一类活怎么填各个阶段，归它的插件。怎么做见设计文档（还没写）；用词以 [GLOSSARY.md](../../GLOSSARY.md) 为准。每条都经 Kun 认过，改之前先问他。

## 要的结果

核心让车间这套自动运转的交付体系转起来：服务于整个系统的目标，让整个系统易于扩展，各部分之间低耦合。

整个系统的目标沿用操作系统目标的第 3、4、1 条：各线自己往后推；同样的结果，Kun 的判断更少；有大局。

不归这里：

- 每一类活的各个阶段怎么做，归它的插件。第一个插件是 issue 交付，它的需求另写一份。
- 执行这一段里面怎么做，由执行者自己定。
- grant-console 是车间的交付对象之一；它自己的流程问题不归车间管，它那套临时循环的经验只当参考。
- 闸口和飞书一侧（收发信、卡片、Ash）是插件，各有自己的需求。

## 要求

### 什么算一件活走完

**R1 任何一类活，你都能说出它走到了哪个阶段。**
阶段是接单、说清楚、执行、证据、审查、交付、验收、收尾，加可选的观察。某类活用不到的阶段可以跳过，执行里面怎么做不规定。
为什么：软件 issue、视频、周报、调研、运维告警五类活现在的做法都能填进这组阶段，不同的只是每一格填什么（11-13 需求对齐页 v4 图 2）。Baton 和 flow-issue-to-prod 都把执行拆成过固定的小步，最后都并回了一步：Baton poc-v7 让接力退役，flow-issue-to-prod 把 8 个节点并成一个。
11-16 补：`workshop status` 只反映当前，默认只列没结束的活（Kun 11-16「Status 应该是反映当前的状态才对。至于看其他的，我觉得你可以加上 all 或者是一些过滤的参数」）；已结束的用 `--all` 看，`--state`、`--target`、`--flow` 筛选，`--html` 写成一页网页（Kun 同日「能不能有一个 HTML 模式？」）。

**R2 登记里没写出 DoD 和约束，车间不接单；跑哪些检查由交付对象的规则登记，不用每张单写。**
为什么：做完了没有，要靠检查的输出判，不靠 agent 自己说；「假做完」是 agent 不守规矩的五种样子之一（见 GLOSSARY.md「假做完」）。核对放在接单，执行者拿到的就是能从头做到尾的活，不再另起一轮去补写登记：#164 起了 16 轮，其中说清楚、证据、交付、收尾各起的模型轮白跑了 6 轮（issue交付 R13）。代价：写登记的一方要一次写全，缺一项整件活不动，`workshop status` 要写明缺哪一项，否则没人知道它为什么不动。
11-19 改（ws#286）：issue 写法改版，加必写的「约束」节，删掉「依据」「能跑的检查」两节，「不可逆或对外的动作」并进约束。统计按旧写法开的 25 张单，「能跑的检查」全是同一行 `scripts/check.sh`，「不可逆或对外的动作」22 张写「无」；单子特有的限制没地方写，ws#280 只好塞进 DoD。Kun 同日「约束必选，可以填 无」「另外两个删除，依据可以在背景里，不可逆或对外的动作可以写在约束里」。

**R3 一件活有没有不可逆或对外的动作，写登记时就在约束里列明，约束里没列就是没有，接单时核对约束这一节在；有的，做到那一步先经用户批一次，在授权中心批（见 [介入点.md](介入点.md) R8）；用户已经交给 agent 判断的那类，不问。登记里没列的不做。**
例：一件活交付时要对外发消息，写登记时就列出来；做到那一步在授权中心申请，用户批了才发。
为什么：给别人发消息、付款、删别处的东西属于「只起草」一档（见 GLOSSARY.md）；已经放给 agent 的再问，就是多花用户的判断。写登记时就列明，执行者开工就知道哪一步要等批，不会做到一半才发现要停；没列的不做，执行者不用临场判断一个动作算不算对外。代价：写登记时漏列的动作，要先改登记才能做。

**R4 DoD 分两段：进交付时查的一段，和交付做完才测得出的一段（例如上线后的行为）。前一段不过，活回到执行，不进交付；后一段不过，活也回到执行，已经交付的结果不自动撤回。两段都过才算做完。**
为什么：防假做完靠检查的原样输出，不靠另一个模型再读一遍：grant-console 7 张验收卡全部点了通过，没有一次退回，真正核对的是检查（issue交付 R6）。有些结果要交付做完才测得出，进交付时查不到，只能放到后面查；不分段的话，这类项要么写不进 DoD，要么让整件活卡在进交付之前。后一段不自动撤回：撤回本身也是一次交付，各类活撤回的办法和风险不同，由插件和规则定（issue 交付见 issue交付 R13）。代价：检查覆盖不到的（界面、文案）要靠亲眼看和「不对」兜底；后一段不过时结果已经在用，只能退回修，挡不住。

**R5 一件活做完以收尾为准；任何一件活停下，都留下工序、送回或等你三样之一。**
为什么：登记与送回是操作系统的机制，停下不留这三样就会丢（见 GLOSSARY.md）。

**R31 一件活可以有前置：前置没完成，这件活不开始跑，记成等前置；等前置不算卡住，不找你，不占执行位置，`workshop status` 写明它在等哪件。前置完成了，它自动接着走。前置完成以前置那件在来源上关闭为准；前置可以属于别的交付对象。**

**R32 一件活可以是总单，下面挂子单：总单自己照常按前置和关口执行、交付；子单全部完成后才收尾。总单自己走到收尾、还有子单未关闭时，显示「等子单」，不派轮、不占执行位置、不发卡或通知；子单全关后自动收尾。活和活之间还可以标「相关」，相关的活作为资料带给 agent，不影响先后。**
为什么：子单挡收尾而不挡执行和交付，总单自己的结果不被子单拖住，可以先交付；总单收尾仍代表整组做完。等子单不派轮、不占位置，等待不花模型也不挤掉别的活。代价：总单交付时子单可能还没做，总单的 DoD 只查得到它自己那部分，要整组一起才测得出的项，要写进最后做的那件子单。挡交付更稳，整组一起交付，但总单做好的东西要一直搁着等子单，搁得越久越容易和子单的改动冲突。

**R33 同一件活上还没处理的事件，攒成一批跑一轮。**
判据：一、worker 取走时，同一件活上所有待处理事件合进同一轮，派活说明里能看到这批事件，按到达顺序；上一轮还在跑时不提前定下一批，等它结束后取走截至当时的所有待处理事件，受单批上限 20 约束，超出的留到下一轮。二、一轮只把它真正带上的事件标成已处理；取走之后到达的事件留在队列，进下一轮。三、同一合批窗口内到达的事件合批；窗口默认 500ms，从第一条待处理事件到达算起，后续事件不重置窗口（固定窗），定批总延迟不超过核心 R27 的 1 秒（窗口只约束空闲活的就绪时刻；运行中的活结束后再把当时所有待处理事件合成一批）；来源可把窗口设为 0（立即取）；单批上限 20，同一件活凑满 20 条不必等窗口到点，立即定批；超出的留到下一轮。四、轮中途守护进程崩了，这批事件按事实表重试，正好处理一次；同一事件不会被两批同时取走。五、标了不可攒批的事件单独一轮，且只在它是当前最小的待处理序号时才取；前面的普通事件先跑一批。六、每个事件序号正好出现在某一轮的批次里一次（R37 判定为陈旧、只留痕的事实除外：它们单独标记为跳过，不进任何批次，也不能把水位推过尚未消费的普通事件，水位只连续推进）。
为什么：连发三条回三次，浪费模型轮次，回复也是碎的。代价：回复会晚到下一次取走；靠上限和窗口到点即定批避免无限等待；上一轮没跑完时不起第二批，跑完后把期间累积的事件合并成一批，不碎批。

**R34 用户可设周期任务，和定时发版共用一套调度。**
判据：一、用户能登记每天/每周 + 时刻（带时区，默认 Asia/Shanghai），到点开一件活。二、到点时间落在持久表里，守护进程重启后正好触发一次，不双触发、不漏触发。三、停机补跑默认只补一次（coalesce_one）：停机期间错过 N 次，恢复后最多补一次。四、重入默认跳过（skip）：按 `schedule_id` 关联，上一件同类活还没结束（含等你、等授权）时，新一次到点不并发开第二件，记一条事实说明跳过；两条同类型但不同 `schedule_id` 的任务互不影响。五、到点开出来的活走同一套接单、阶段和关口。六、重复跳过不能把周期任务静默停掉：连续 3 次 skip，或上一件等你、等授权超过 24 小时，记一条 `schedule_starved` 事实，在 `workshop status` 里显示；不给你发消息。同一条挂起只落一条，不刷屏；挂起活结案后不再显示、skip 计数归零。
为什么：文章里定时由用户设、跟进由 agent 设，车间已经会后者，缺前者。代价：先只支持每天/每周 + 时刻；cron 表达式留到有需要时。

**R37 推送式来源：入口快速应答，和轮询共用去重键。**
判据：一、来源可以在事件发生当下推给车间；入口在 2 秒内完成验签、原子写本地 spool、叫醒守护进程并回 2xx，不在请求里等 worker 或模型；签名错误、缺签名、未配 secret 一律拒收；守护进程不在线时仍落盘并回 2xx，等它启动后补消费。去重和写事实表由守护进程做，入口进程不打开事实表。二、同一次外部变化，推送和轮询写进事实表的 `(source, ext_id)` 必须一样；`ext_id` 取对象 id + 变化类型（action）+ 该变化在推拉两边都有的标识（如标签名、评论 id）+ 对象版本或 `updated_at`，不能只用对象 id，也不能用只有一边有的 delivery id（反例：同一件事推送用 delivery id、轮询用 comment id，落两行跑两轮）。同一秒内同 action、同标签的重复变化可能撞键，接受这一限制；撞键时以轮询的当前快照校正状态（例如加、去、加之后最终状态是有标签），不凭去重后的行数推状态。不同 action 或不同标签不撞。升级时旧事实用旧键，要有迁移，但只能用可从事实表重建的独立别名映射（纯派生层，不破坏 #314 中 memory.db 为唯一不可重放派生层的口径），禁止原地改写事实表旧行（核心 R7）；迁移后不能让轮询或推送把同一批旧数据按新键再落一遍、把旧活重新叫醒。三、陈旧判断只用于状态覆盖类变更（改状态、改负责人、关/开）；增量类变更（新评论、@提及）按自己的 id 和到达顺序处理，不因对象版本更新而丢弃。乱序或陈旧事件照常追加留痕，但不把活的状态往回拨，不触发执行者空跑；陈旧事实单独标记为跳过，不进入 R33 的攒批（R33 判据六的明确例外），也不能把水位推过它后面尚未消费的普通事件，水位只连续推进；状态水位持久化，重启后仍能判定陈旧。四、推送通道不可用时退回轮询，不漏事件。
为什么：车间现在只有轮询；文章说 webhook 是常驻 agent 的主要来源之一。代价：推送要先有对外入口，部署方式和授权边界先定；这一条排最后。同秒撞键的限制：GitHub 的 webhook 载荷不带标签事件的事件号，两边共有的只有标签名和秒级时刻，同一秒里同一标签加两次只落一行；状态以轮询读到的快照为准，行数只说明「有过这类变化」。
11-21 落地（ws#315）：默认关闭，交付对象的 `sources` 列出 `webhook` 并写 `webhook` 配置才起入口（`workshop webhook --target <交付对象>`），只许绑 loopback；这一单不对外开端口，对外入口、域名、secret 归属另定。

### 什么算事件

**R6 让一件活开始或往下走的都算事件，包括你直接给 agent 发的消息。**
你在 Orca 里直接对一个写代码的会话说「这里换个做法」：这算那件活的一个事件，核心记下来，不改派，也不拦。
为什么：不记下来，R9 查一件活为什么这么跑就缺一块。

**R7 同一个东西上的事件，在同一个流程里归到同一件活；一个事件可以同时触发几个流程，各开各的活。一件活同一时间只跑一轮，同时在跑的活数有上限。**
例：同一个 issue 上接连来了三条评论，你看到的是一件活往下走，不是三个会话同时在改。一个 PR 合并了，issue 交付那件活往下走，另一个也要这件事的流程另开自己的活。
为什么：grant-console 现在写死同时 2 个，其他系统各管各的（11-13 需求对齐页 v4 图 4）。一事几个流程：Kun 11-14 回「可以」。

**R27 事件进到车间，1 秒内开始处理；车间不按固定间隔去看有没有事。作业做完、卡片有了回答，也算事件。**
生产主循环一拍的 tick_ms 稳定在 100 毫秒以内。
为什么：Kun 11-14：「为何要加sleep？拿到事件就处理不好么？」现在主循环每拍后睡 2 秒，一件活往前一步至少等一拍。

**R28 外部来源上的变化（例如 GitHub 上打标签、评论），30 秒内进到车间；那边配了推送的，10 秒内。**
为什么：11-13 从状态库量的，GitHub 上打标签到车间记下事件，workshop 中位 98 秒、最长 641 秒，grant-console 中位 40 秒、最长 143 秒；来源每次把接过单的对象全查一遍。30 秒是 Kun 11-14 认的。

### 什么算服务于整个系统的目标

**R8 你问「现在都有什么活」，看到一张图：每件活在哪个阶段、谁在推、下一步是什么、卡在谁手里。**
为什么：这是操作系统目标第 1 条「有大局」的原话落到活上。

**R9 你问一件活为什么这么跑，一条命令看到它每一轮的起因和结果。**
为什么：现在 `~/.local/state` 下有二十多个账本目录，查一件事要翻好几处（11-13 需求对齐页 v4 图 4）。

**R10 你看得到每件活、每天和最近 7 天花了多少 token 和钱；每一轮的记录够你按模型、按执行者配置档对比着复盘。**
每一轮记：规则要的模型和推理强度、实际用的模型、开始和结束时刻、输入、缓存读、缓存写、输出四种 token、花费和计费方式（订阅或按量）、这一轮的结果；拿不到的记「未知」，不记 0。订阅的花费也按 API 标价折算，各模型才能用同一把尺子比。缓存命中率是缓存读除以全部输入。
为什么：ai_quota 只看订阅额度，按轮的花费现在没处看。Kun 11-13：「执行记录里要包括：1. 使用的是什么模型。2. 花了多少时间。3. 多少Token。4. 花了多少钱。5. 缓存命中情况。总之，要有完整的历史，方便后续复盘。」Kun 11-19 要让几个写代码的执行者轮着做活、比效果（#281），同一个模型配不同提示词或 skill 的配置档要分开比。

**R30 你问「车间运转得怎样」，一条只读命令按小时给出三段数字：供给（开着没收尾的活、还没轮到开工的活及最老一件等了多久），流动（每件活在途时间里在跑、定时、卡住、排队、等你各占多少，失败轮占比，卡住、等你、排队里最长的一件），负载（执行位置占用）。**
为什么：Kun 11-16 要快速看到反馈，用引导指标看系统是否在适当负载下持续运转；确认「供给→流动→负载」框架和 `workshop metrics --since 24h` 按小时出数。11-16 改：登记写全并带 Ready for Agent 的 issue 按优先级排队，标签由车间核对后自动补齐，也保留用户亲手打标签和会话放行（[介入点.md](介入点.md) R4）。

**R11 agent 说「半小时后再看」，到点它自己接着干，你不用提醒。**
为什么：现在每个系统各写一份等待和轮询。

**R12 一件活等你回答、等授权，或等它订阅的别的事件时，不占着会话、不花 token；等的到了，车间唤起原来的会话接着往下走。**
为什么：Orca 会话现在开着等。11-16 扩：Kun「没授权就停下，车间要能做到能冷唤起agent，当它要的授权或者订阅的事件到了，就唤起它」「接回原来的」。

**R13 一轮跑完，它要你的、约好再看的时间、订阅的事件，都记进车间，不只写在会话的文字里。核心记这件活停在哪一步、在等哪一项（只是一个引用）；等你的问题、你的回答、推给你的消息，由介入点插件记。**
为什么：收尾句和交接现在是文字约定，盯梢要靠读文字认。11-16 补：Kun 在「车间介入点实施设计」选「统一介入点插件管理全部交互」「独立插件服务与持久记录」；核心不认卡片、问题和送达的内容。

**R14 一件活反复跑不成，它不会一直重试下去；部署里配了执行者阶梯的，先逐级换更强的执行者接着做，到顶仍不成，车间才启动项目经理去处理（见 [介入点.md](介入点.md) R11、R12）。**

### 什么算易于扩展

**R17 加一类新活（比如每周的 Steam 选题信号），写一份规则加 skill，或写一个插件把各个阶段填上；核心不用改。**

**R29 每个交付对象在规则里列出它用哪几个流程，每个流程配各自的触发器；同一个流程在不同交付对象下可以配不同的条件。加流程、改触发条件只改规则，流程插件和核心都不动。**
例：workshop 用 issue 交付（GitHub 上开 issue）和定时发版（workshop 每 10 分钟一个窗口，周期写在规则里）；grant-console 只用 issue 交付。几个交付对象相同的部分用 YAML 锚点共享，不另做继承。
为什么：Kun 11-14：「要实现事件机制，还要能让事件触发各种流程」「要不要考虑一下不同的交付对象分开配置呢？」现在一个交付对象只绑一个流程，标签名、kun-g、「不对」写死在 GitHub 来源里。

**R18 换一个执行者（比如审核从 Grok 换成 Codex），只改规则或部署目录里的一处；改部署目录的，校验后重启车间就生效，不用发版，插件和核心都不动。**
为什么：额度用完、模型换代都会换执行者，每换一次都要改插件或核心，就谈不上易扩展。

**R24 每一轮挑哪个执行者、用什么模型和推理强度，由规则里写明的一段挑选逻辑定；换逻辑不改核心，每一轮记下挑它的理由。**
例：第一版只带一段逻辑：按规则里的顺序挑第一个有额度的，审查和验收跳过写代码的那家；攒够 R10 的记录，再定下一段。
为什么：Kun 11-13：「执行具体任务的模型可以切换，甚至可以用一个逻辑来控制。」先便宜后贵、按难度挑这类逻辑，现在没有数据定分界线，Kun 11-13 选了先攒记录。

**R25 同一个执行者（比如 Claude Code）可以在规则里写成多套配置档。每套各自写明模型、推理强度、提示词或 skill、工具和权限、MCP、插件和 settings、账号或配置目录。加一套配置档只改规则，或在部署目录里加一个目录，插件和核心都不动。**
例：写代码用一套，排错用另一套；审查和验收默认用「只读审查」这套，效果和 11-13 时一样。
为什么：Kun 11-13：「如果我想用Claude Code，但使用不同的配置，通过这种方式让它适应不同的任务，这种情况下，这个执行器能很简单地支持吗？」需求草稿经 Kun 回答「可以了」。

- 配置档写在唯一规则文件里；部署也可以在自己的部署目录（默认 `~/.config/workshop/`）里一个目录加一套，或同名整个替换规则里的那套，校验后重启车间生效，见 [executor-profiles.md](../executor-profiles.md)（ws#293）。每套有名字，各阶段候选的 `use` 引用配置档名。会话、不可用、返工（`retry_executor`）均按配置档名区分；同一件活前后换配置档，开新会话。同一 CLI 的不同配置档仍算同一家（`family`），配了网关的例外，见本条末尾。
- Claude 和 Codex 支持提示词/skill、工具权限、MCP/插件/settings、账号/配置目录四类。Cursor 支持模型、推理强度及权限模式；默认 `plan`。Cursor 权限模式入配置由 Kun 在 ws#62 问卡 `cursor-mode` 选择 `config-mode` 确认（事实 4845）。每套另写运行方式（Orca 终端交互或后台无人值守），与 CLI 分开。
- 驱动不支持的字段或拼错字段，在加载规则时给出配置档名和字段名并报错，不能先启动任何会话。每个启动配置项必须到达 CLI 的参数或环境，以 argv/env 断言验证，不依赖用户全局配置补齐。
- 工具白名单、plan 权限、空 MCP、只读沙箱来自规则里的只读审查配置档，执行者不按阶段自行添加。默认审查和验收启动参数与迁移前相同。
- 审查、验收仍强制清理部署凭据：GH_TOKEN/GITHUB_TOKEN、SSH agent、AWS/Azure/Google/K8s 变量、git credential.helper；GH_CONFIG_DIR 指向本轮空目录。配置档不能取消这项清理。
- 迁移沿用 `orca-claude`、`orca-codex`、`codex`、`cursor-grok`、`claude` 名字，在途会话可接回，model/effort/billing/quota 不变。按任务类型挑配置档不在本件范围。
- 写代码的执行者不加载用户本机的个人配置（设置、hook、全局指令），只用规则和它自己目录里的配置；登录沿用本机订阅（配了网关的例外，见下一条）。Codex 的执行者在它的 CLI 支持之前例外，仍加载个人配置。（ws#283）
- 配置档可以指定一个本机网关，让某个执行者的壳去跑另一家的模型；这样的配置档按模型算哪一家，审查和验收照这一家回避，登录用网关的，不用本机订阅登录。（ws#287，Kun 11-19 在协调对话同意「审查规则按模型算」）
- 执行环境默认是 Orca 的终端，配置档可以写明在后台跑；部署可以用一个开关整体关掉 Orca，关掉后全部在后台跑。（ws#293）

**R26 接一个新的命令行 agent，只加它自己的一份接入代码，别处不用改。**
具体为一个驱动文件和一条入口点注册；公共启动、包装进程、用量入口和钩子不增加按 CLI 名字分的分支。

为什么：易于扩展在加新流程时评判，算在观察这一段；不放一条固定的检查，就不会有人去评。

## 约束

**C1 外部的文字（issue 正文、网页、别人发来的消息）只当资料交给 agent，不当指令。** 来自：安全。

**C4 订阅和按量计费的执行者一样参与挑选，每一轮记下计费方式和花费；要加购订阅额度，先问你。** 来自：花钱由 Kun 定。
