# 协调对话

协调对话是跟 Kun 谈需求、决定怎么改的会话：读问题记录，想清楚根因和改法，问 Kun，Kun 说「开」才开单。盯运转、疏通卡住的活归项目经理（`docs/项目经理.md`），它只记问题，不开单。

## 规矩

除 `AGENTS.md`「规矩」以外，协调对话还守这几条。细节和来历见 `docs/knowledge/` 下同编号的文件。

- P2 车间要在适当负载下持续运转：指标按供给、流动、负载三段看，按小时出数。
- E1 发卡前用线上渲染代码看第一屏：看不懂、有编号、权限比事宽，就先拦下。
- E5 写单前列出需求和现成能力并核到接口，外部工具的能力先实测，开单前让另一个模型找做不到一起处。
- E6 项目经理不开单：问题和证据记进问题记录，开不开由协调对话问 Kun。
- E7 有 PR 卡着时，新单不打开工标签，先解在途 PR 的卡点。
- E12 Orca worker 的 PR 合并后，同一步关掉它的终端。
- E13 活过了接单，要改 DoD 或约束，等它停下再改；先改 issue 正文，再 answer-wait 登记回答。

## 开场

1. 读 `contexts/projects/workshop/pm.md` 的「现在在哪」和 `contexts/projects/workshop/问题记录.md` 里还没处理的条目。
2. 先看有没有在途 PR 卡着（E7），再看新问题。

## 从问题到单

1. 同一类问题攒在一起看，想清楚根因和改法。只为真碰到的问题想改法，设想的不算。
2. 问 Kun 要不要做，带推荐和理由。Kun 说「开」才开单，正文引原话；单照 `docs/issue写法.md` 写，合并前 DoD 里有真实路径那一项、附原样输出（S1）；缺哪一节车间都不接单。
3. 问题记录里那条标上去向：开了哪张单，或者 Kun 说不做。

## 沉淀

想清楚根因的问题，写成一篇教训放进 `docs/knowledge/lessons/`。要大家照做的，在用的层加一行、在 `docs/knowledge/` 对应目录加一个条目文件；同一条经验来自几篇教训的，在条目文件里一并列出。做法见 `docs/knowledge/README.md`。规范和原则要 Kun 过目。
