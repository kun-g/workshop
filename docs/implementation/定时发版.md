# 定时发版

落实定时发版 R1–R5、issue交付 R3；独立看门负责回退。本流程不修改核心、不引用其他插件。依赖核心已有的程序阶段和多流程规则。

## 规则

唯一入口为 `rules/workshop.yaml` 的 workshop 交付对象：

```yaml
sources: {github: {}, main_branch: {every: 1h}}
default_flow: issue_delivery
flows:
  issue_delivery: {triggers: *issue_triggers}
  scheduled_release:
    triggers: [{source: main_branch, when: {kind: ahead}, action: ready}]
    scheduled_release_state_dir: ~/.local/state/workshop
release: none
```

`main_branch` 和 `scheduled_release` 通过 pyproject 入口点注册。状态目录须指向该守护进程的状态目录（与 `workshop --state-dir` 相同），其中有心跳和唤醒 socket；隔离运行必须一起改两处。来源只支持 `every: 1h`，其他值报错。沿用对象的 `checkout`、`repo`、`github_identity`、`prepare`、`check_timeout`、`release_timeout`。

## 来源与归件

当前 UTC 小时整点的 ISO 时间是游标。进入新时段后的第一次 poll 比较本地主检出 HEAD 与远端 main；启动时无游标也比较一次。相同时段的后续调用不发网络请求。请求失败抛 Retryable，由核心退避，不将失败当作没有新提交。

相同则无事件；不同则发 `kind=ahead, from=<完整 HEAD>, to=<完整远端提交>`，对象号固定为 to，事件外部编号为时段。核心将事件分给定时发版流程，活号是 `workshop:scheduled_release:<to>`。同一提交跨时段归同一活，完成后收到 ready 仅补资料，不重新运行。新提交另开一件。远端回退或分叉也可能产生事件，交付阶段的祖先检查拒绝倒退和非快进。

来源从定时发版流程配置取得状态目录（即使当前拿到的是 issue 默认流程配置）。`release.json` 为 rolled_back 且远端 main 仍为其中的 to 时，只推进小时游标，不发事件；有更新的合并时下个整点照常发版。记录损坏时报 Retryable，不能把读取失败当作可以重发。

访问 GitHub 使用规则中的 App 身份，签发失败不回退个人身份。检查和 prepare 运行在仅保留路径、语言和临时目录变量的环境，使用临时 HOME，不继承部署凭据或个人 Git 配置。

## 程序阶段

为满足核心关口，流程保留接单、说清楚、执行、证据、交付、验收、收尾七段，全部 `automatic=True`。前三段只登记固定提交与 `[["scripts/check.sh"]]`，不启动 agent。

- **证据**：取固定 to，在主检出下建立独立 detached worktree，运行 `scripts/check.sh`。结果以 argv、exit_code、stdout、stderr 原样保存在本活文件中，再收回本插件创建的检查副本；清理失败另留 cleanup_error。检查失败、超时或缺命令都标 failed，后续阶段不做上线动作，只收尾。
- **交付**：在共享发版锁内核对 main、干净工作目录（包括未跟踪文件）、可以快进。只快进到已检查的 to，按规则 prepare 顺序执行。失败记录已快进事实，不重启。每条 prepare 在执行前登记 running，成功后保存结果；中途进程消失而结果不明时不盲目重做，记录失败供处理。
- **验收**：持久记录重启前的父守护进程 PID 和启动时间。新作业必须看到不同父身份，且旧身份已退出、主检出仍为 to；随后向本地信箱发唤醒，最多在作业进程等待 5 秒，要求 heartbeat.last_ok_at 晚于本次探测起点，最后再次核对父身份稳定。这样不会把旧进程最后一拍的心跳认作新进程成功。通过才写 ok。
- **收尾**：成功发一次完成通知。失败只发失败通知；都经 After.notice 交核心去重，`notices: hold` 时只记事实。失败提交不会因下一整点而重检。

确认尚未满足时返回 pending，由核心约时再查，不启动会话。原有核心 pending 次数及退避不变；正常新进程由唤醒主动写心跳，可以在当次确认作业完成。生产交付必须运行在 `workshop run` 的后台作业中；`run --once` 不兑现重启请求，因此拒绝用它上线。

## 持久记录与幂等

每件活的记录：`<state-dir>/scheduled_release/<sha256(活 ID)>.json`，保存固定提交、检查原始输出、准备命令结果、失败原因、每个 after key 的结果。文件写临时文件、fsync 后原子替换；共享 `scheduled-release.lock` 避免两个发版动作同时修改主检出。

检查已开始但结果未确认的异常退出不重跑同一提交。完成的 after key 重放读记录，准备命令成功结果不重做；新守护进程重放交付钩子时不再次请求重启。核心自己的作业目录和执行轮记录不被改动，原有重启认回机制继续生效。

成功 prepare 后，在请求核心重启前写 `<state-dir>/release.json`：

```json
{
  "from": "发版前主检出的完整提交号",
  "to": "已检查的完整提交号",
  "at": "2026-11-14T10:00:00+00:00",
  "status": "restarting",
  "prepare": [["uv", "sync", "--locked"]],
  "prepare_cwds": ["."],
  "item": "workshop:scheduled_release:<to>",
  "daemon": {"pid": 123, "start": "Sat Nov 14 17:00:00 2026"}
}
```

`prepare` 保持 argv 列表契约；`prepare_cwds` 与它按索引对应，默认相对主检出 `.`。确认后 status=ok，增加 confirmed_at、confirmed_daemon。另有一件 restarting、rolling_back 或 rollback_failed 发版时，新发版只等待，不覆盖其记录。

## 独立看门回退

看门仍由 launchd 每 60 秒用系统 Python 和 `-I` 直接运行 `src/workshop/watch/__init__.py`；仅用标准库，不加载插件或项目虚拟环境。它只读 `workshop.db` 的 `controls/@rules` JSON 快照，找出配置到本状态目录的唯一 scheduled_release 交付对象，取得 checkout、release_timeout 和 notices。无法确定配置时不猜主检出，原因留在 watch.json；不会修改核心数据库。

持有 watch.lock 后，以非阻塞方式取得与发版作业相同的 scheduled-release.lock，取锁后才重读 release.json。锁忙就留到下一次看门，保留之前的通知去重标识；这次没有观测不能当作故障恢复。只有 restarting 且距 at 超过 180 秒时尝试；ok、180 秒以内（含边界）、没有记录均不回退。

回退前检查 main、工作区干净（包含未跟踪文件）、HEAD=to、from 是存在的完整祖先提交，以及 prepare argv/cwd 合法。失败不改主检出，只记原因。工作目录在 reset 前后都解析并检查不能越出主检出。回退顺序：

```text
restarting
  → rolling_back（先原子落盘）
  → git reset --keep from
  → prepare（按 prepare_cwds；缺省 .；清掉部署凭据）
  → launchctl kickstart -k gui/<uid>/com.kun.workshop
  → rolled_back + rolled_back_at
```

每条命令调用前写 rollback.pending，调用后写 rollback.runs，保存 argv、cwd、exit_code、stdout、stderr。失败即停止后续命令，标 rollback_failed，记录 rollback.reason；命令超时用 124、启动失败用 127。若进程在动作期间退出，下一次读到 rolling_back 会标结果未确认，不盲目重复 reset/prepare/kickstart。rolled_back 仅表示命令已完成，不表示新版本已成功上线，也不凭空声称旧版本恢复了心跳；心跳仍由现有独立告警检测。

发版流程在读取已完成阶段结果之前核对回退状态。相同 item/to 已被看门停止时，把发版活记失败并结束，不能重放旧的重启请求或成功通知；不改变其他执行轮、作业的接续。新发版在失败回退记录尚未处理时等待，不覆盖证据。

回退通知使用 watch.json 的持久标识、现有 ask-kun 通道及 attention 兜底，通知失败后只重试同一 request-id，不重做回退；hold 只记录 via=held。观察到回退结果就可通知，不额外等待第二次看门。已有心跳、通道、超时轮告警仍独立运行。rolled_back_at 的每个记录对应一次回退，不按看门运行次数计数。

rollback_failed 需要负责会话核对记录中的已完成命令、实际 HEAD 和依赖环境后处理；看门不自动重做结果未确认的动作。成功回退后的新合并由来源自动唤醒，无需 Kun 点继续。

workshop 的 issue 交付只合并并立即进入自己的验收，不再带 `_self_update`。在途作业携带的旧 `release: self` 快照按只合并兼容，避免升级后卡住。grant-console 的 tag/线上核对路径保持原样。部署本改动后，首次实际整点的 why 可作为补充证据贴回 #77（评论带车间标记）；开发与验收只在临时仓库测试，不动现役车间。

## 验证

`tests/test_scheduled_release.py` 使用真实临时 Git 仓库、可控时钟和进程/网络替身；验证时段游标、固定提交、失败/通知去重、主检出保护、prepare 失败、父进程与新心跳确认、后台作业恢复及不占执行轮，并覆盖 rolled_back 提交过滤、新合并再试、旧阶段结果不得重启或通知成功。`tests/test_watch_rollback.py` 覆盖系统 Python 独立回退、180 秒边界、主检出保护、命令失败原样记录、中断不重做、锁互斥、send/hold 和通知失败重试。`tests/test_ask_kun_watch.py` 回归已有告警；`tests/test_rerun_acceptance.py` 验证 issue 合并不更新主检出、不重启。总检查仍为 `scripts/check.sh`。测试只动临时仓库及状态，launchctl 和通知使用替身。
