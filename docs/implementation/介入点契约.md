# 独立介入点服务与通用等待契约

依据：核心 R9、R12、R13、R16、R17、R20、R21、R22、R23；介入点 R1、R5、R7、R8、R9、R12、R13、C1。需求定稿来自 #179 / PR #185，本单不改需求。Related to #172。

## 本单边界

新增独立服务、持久记录、可供流程使用的端口及核心暂停/恢复。既有流程未绑定新等待、既有通知出口未切换；本单没有把旧核心里的卡片记录迁走。迁移由后续单完成，不能把本单合入理解为现役交互已经全部切换。

核心不处理问题、回答或送达内容。它只收引用与完成标识；完成标识只表示“有结果可读”。否定回答也能唤醒，是否继续、拒绝后如何处理由原阶段再次核验，核心不会把超时、空响应或一次唤醒当批准，也不会在收到完成信号时跳到下一阶段。

## 记录归属

| 内容 | 权威记录 | 标识与重试 |
|---|---|---|
| 等待的问题、所属活、介入点类型 | 独立服务 `intervention.db` 的 wait 记录 | 创建操作号；同号同请求返回原引用，同号不同请求拒绝 |
| 回答、原话、会话号或回源证据 | 同一 wait 记录与追加 journal | 回答操作号、结果 token；同一等待不覆盖已有答案 |
| 送达许可、原因及作用范围 | 服务 permit 记录 | `point + scope` 去重；取消持久化 |
| 待发送内容、发送意图、外部编号 | 服务 delivery 记录 | 每个许可最多一份内容，固定 delivery id 传给通道 |
| 各操作请求及返回值 | 服务 operations 表 | 全局操作号绑定 action 与完整数据 |
| 暂停位置、服务名、等待引用 | 核心 `wait_bound` 事实及 waits 视图 | 绑定操作号，全局唯一；一个引用不能跨活或跨阶段使用 |
| 完成信号已消费、确认是否完成 | 核心 `wait_resumed` / `wait_changed` | 恢复与活状态同事务；提交后才向服务确认 |

两边 SQLite 都启用 WAL 与 `synchronous=FULL`。服务的 journal 只追加，核心继续使用现有事实日志及可重建视图。两边没有共享数据库、跨库 SQL 或跨插件 import。

## 协议和流程接入

服务监听当前用户私有目录里的 Unix socket（目录 0700、socket 0600）。JSON 一行一个请求：`{"action":"create","data":{...}}`；返回 `{"ok":true,"result":{...}}` 或 `{"ok":false,"error":"..."}`。请求上限 2 MiB；未知字段拒绝。只有当前系统用户能操作，和既有车间相同，这不是隔离同用户 agent 的安全边界。

服务操作：

| action | data 必填字段（除只读操作外） | 结果 |
|---|---|---|
| create | operation、point、owner、content（非空对象） | ref |
| answer | operation、ref、value、source | ref、token |
| ack | operation、ref、token | ref、token |
| permit | operation、point、owner、scope、basis | ref、cancelled |
| enqueue | operation、permit、payload（非空对象） | ref |
| cancel | operation、ref、reason | ref |
| get / status / dispatch | ref | 完整业务记录 / ref+ready+token / 发送状态 |
| ping | 空对象 | protocol=1 |

`source` 为会话时必须带 `channel=session, session, quote`；外部系统时必须带 `channel=external, reference, evidence`。调用方负责回查真实身份、回答和动作终态，不能凭外部正文自称“已批准”调用 answer。服务不代替授权中心、不自行签发业务批准；外部批准与动作真正生效的核验由授权接入单补齐。

核心端口 `WaitService` 注册于 `workshop.wait`；当前实现名 `intervention`。流程不自己建 Registry 取端口。定了的做法是核心调完成钩子 `after` 时传一个只读句柄，按规则 `wait_services` 的名字给出等待端口和它的配置，像 `classify` 拿到的 `find_external`，在作业进程里现做；句柄已由 #173 落实。流程用端口的 `create/read/invoke`，不 import 另一插件。`invoke` 的业务内容不会进入核心等待事实。

流程完成钩子示例（`service` 和 `config` 从核心传入的句柄取得，由核心提供）：

```python
# key 是核心传入的稳定完成钩子号；不可用随机操作号重试。
ref = service.create(key + ':question', {
    'point': 'decision', 'owner': item['id'],
    'content': {'question': question, 'recommendation': recommendation},
}, config)
record = service.read(ref, config)
if record['answer'] is None:
    return After(pending=True, reason='等待取舍', next='原阶段核验回答',
                 wait={'provider': 'intervention', 'ref': ref,
                       'operation': key + ':pause'})
# 必须解释原回答并核对来源/目标，不因 ready=True 直接返回通过。
return assess_answer(record['answer'])
```

核心把 `After.wait` 与 pending 一起处理：持久保存原阶段、引用和原完成钩子，结束执行轮；等待不占执行者。首次启动立即对账；后续由服务提交后的 `.changed` 文件事件唤醒。读到未完成时有 60 秒漏信兜底；暂时故障 5 秒后重试，同一拍的网络查询通过既有 Jobs 机制放到独立进程。收到有效完成标识后原阶段重新执行完成钩子，才能决定继续、阻塞或新建等待。新问题必须使用新操作号，旧等待不能重新挂回。

## 恢复和失败行为

| 中断位置 | 恢复后的行为 |
|---|---|
| 创建已提交，ref 未送回 | 同 create 操作号返回原 ref |
| 核心绑定已提交，调用方未收到确认 | 同绑定操作号认回原暂停；参数冲突拒绝 |
| 回答已提交，确认未送回 | 同 answer 操作号返回原 token，回答不覆盖、不重复记 |
| 核心恢复已提交，服务还没收到 ack | waits 记录为 resumed；重启只补 ack，不再恢复一次 |
| ack 已提交，核心没收到确认 | 同 ack 操作号返回原结果，核心补记 acknowledged |
| 插件退出、拒绝请求、超时、空结果、结果引用不匹配 | 活保持暂停；记录故障类型，不隔离别的活 |
| 活已放弃、完成、暂停位置变了 | 旧信号标 superseded，不改变新位置 |
| 交付对象暂停 | 保留结果，恢复对象后才消费 |

同一活的新来源事件不会越过有效等待；返工仍留着，待已订阅的结果到达后按原机制处理。其他流程和执行者不因一个等待查询失败而停下。

## 许可与送达

目录和准入字段只在 `rules/workshop.yaml` 的 `intervention.points` 中。普通需求确认、执行取舍、授权结果等待、暂停补选只等待，不发通知；亲眼看、盯更新报告以及项目经理确有结论后的求助按各自已有约定取得许可。授权中心自己的卡不经本服务重发。

亲眼看的许可必须带约定、查看位置、回复方式；报告带约定与产物；求助带要 Kun 做的一件事、原因、证据和状态栏位置。求助 `idle:<空闲段号>` 共用一次额度，`incident:<事项号>` 按事项一次；亲眼看按 `contract:<约定号>`，报告按 `report:<报告号>`。这些号及“是否已经自行解决”由各业务接入单核验并持久登记；本单不自行判定空闲段或启动项目经理。

`enqueue` 先保存内容。`dispatch` 先重新核对许可，再持久保存 sending，随后调用通道。超时/断开/异常回执一律 uncertain。下一次先 reconcile：sent 记外部编号，unknown 保留等待，只有 absent 才可用相同 id 重试。许可取消且确定未发时不再发送；许可取消前已发送但丢确认的，仍记录真实送达，不伪装未发。

`intervention.transport` 已配置飞书私聊命令；合并前隔离回放只替换收件端为本地收件箱，没有旧通知口回退。命令从 stdin 收 `{"action":"send|reconcile","key":"稳定送达号","payload":{...}}`，stdout 返回 `{"state":"sent","external":"..."}`、`{"state":"absent"}` 或 `{"state":"unknown"}`。通道必须按 key 去重和回查；非零退出或不合规返回不会被当成功。一次外部调用最多 20 秒；服务串行处理，请求端超时重试前先对账。

## 独立安装与外部重启

从本 worktree 构建独立 wheel；它只包含介入点插件、共用 Unix socket 客户端和 PyYAML，不包含核心、其他插件或主状态库。PyYAML 是仓库已有依赖，本单未新增依赖。

```sh
uv build --wheel --out-dir .local/intervention-dist standalone/intervention
uv venv --python 3.13 /绝对路径/intervention-env
uv pip install --python /绝对路径/intervention-env/bin/python .local/intervention-dist/workshop_intervention-0.1.0-py3-none-any.whl
/绝对路径/intervention-env/bin/workshop-intervention \
  --state-dir /独立状态目录 --rules /规则位置/rules/workshop.yaml \
  --endpoint /私有目录/service.sock start
```

独立服务和核心都读取同一份规则；不要复制成第二份业务配置。仅 socket、状态目录和解释器是安装参数。外部看门可调用独立环境里的 start（已在运行时只检查存活）；它不会启动核心、打开核心库或修改主检出。要进程级自动恢复，用 `plist --output <路径>` 生成 launchd 定义，部署阶段再 `launchctl bootstrap`；`restart` 使用 `launchctl kickstart -k gui/<uid>/com.kun.workshop-intervention` 重启该独立任务。生成定义不加载服务，本单没有在现役注册或重启任何任务。

独立性检查：在独立环境用 `python -I` 导入 `workshop.plugins.intervention.service` 应成功，`importlib.util.find_spec('workshop.core')` 应是 None。现场查看/重启不需要车间主环境能 import。

## 验证与复跑

固定检查：`scripts/check.sh`；新增回归在 `tests/test_intervention.py`，故障等待使用管道、真实进程退出和假时钟，没有测试 sleep。

真实路径回放脚本 `scripts/verify_intervention.py` 需要 App 回源的 issue JSON 和车间已登记的会话原话事实 JSON；两者只读导出到本地文件，不含令牌。脚本只使用自己启动的进程、临时 socket 和独立状态库，不碰生产进程、生产库或真实发送通道。它先用独立环境创建服务，再用本安装的真实 Engine 创建来源活、暂停、重启、重放和确认，故障钩子只在验收子进程里拦住“已提交、未返回”位置。

```sh
uv run python scripts/verify_intervention.py \
  --rules rules/workshop.yaml \
  --issue <App回源的issue.json> --answer <已登记的会话事实.json> \
  --service-python <独立环境>/bin/python --output .local/intervention-evidence
```

通过标准：创建、回答、确认各一条；核心 wait_bound 和 wait_resumed 各一条；插件停止期间仍等你；恢复后阶段仍为暂停前阶段、approved 未增加；未登记的 progress/completed 许可被拒绝；核心库离线且独立环境不能 import 核心时 start 仍成功。标准输出逐步含命令、退出码及原样输出，输出目录另保存两个数据库快照、输入和 transcript.json。真实飞书送达与生产迁移没有在此脚本验证，交由各接入单和最终迁移验收，不能把隔离回放说成生产已切换。


### 隔离发送的进程级验证

`scripts/verify_intervention_delivery.py` 使用真实独立服务与真实 `Service.transport → subprocess.run(argv)` 调用链，只把外部收件端替换为写本地 SQLite 收件箱的验收进程。脚本读取唯一规则的验收副本，仅配置该副本的 `transport` argv；目录、许可准入规则保持原值，不形成生产第二份规则，也不注册现役服务。

```sh
uv run python scripts/verify_intervention_delivery.py   --rules rules/workshop.yaml   --service-python <独立环境>/bin/python --output .local/intervention-send-evidence
```

四条路径：unknown → 真正的 20 秒子进程超时 → 重启 → reconcile absent → send sent；收件箱已落盘、回执前终止服务进程组 → 重启 → reconcile sent；排队时取消；不确定发送后取消且 reconcile absent。故障使用 FIFO 闸门，不 sleep，不 monkeypatch 服务方法。脚本断言调用次序、送达次数、记录保留及 sent 后再次 dispatch 不调用通道。每条操作和响应、服务版本、状态目录、argv、退出码、两侧记录保存在输出目录。

## 完成钩子直接调用（#173，H8）

五条同时满足：被调方自己持久记结果、稳定操作号幂等；核心不用区分谁坏了；不开会话、不占并发或串行名额；经核心定义的端口，装配对象由核心只读句柄交出；只在流程 after 内短时调用，不另起后台轮询。

| 情况 | 处理 |
|---|---|
| 被调方明确拒绝 | 端口抛 WaitRejected，调用方返回 After(blocked=原因,next=修正动作)，只卡本活 |
| 暂时不通或响应不完整 | 端口抛 WaitUnavailable，调用方返回 After(pending=True)，原操作号重查；达到 pending_limit 只卡本活，不隔离流程 |
| 调用方自身错误 | 按原有流程故障处理，不伪装成暂时不通 |

`intervention.points.<名字>.required_wait` 是建等待时的必填字段列表。decision 要 key、version、stage、question、reason、recommend；owner 在外层，started_at 由服务第一次提交时记录。缺字段明确拒绝。服务启动和业务操作时校验 intervention；等待客户端只校验 endpoint/timeout，超时上限 30 秒。

问题版本与内容绑定，同版不能改内容。新版本取代同活、阶段、问题 key 的未答版本；旧等待拒绝新答案。会话回答 source 保存 channel=session、quote、session、version；重复请求返回同一 token，不重复恢复。status/why 经 read 查看，核心不保存问题或答案正文。


## 授权和业务送达接入（#174）

`Evidence.action_targets` 是动作到确定目标的映射；`authorized_actions` 每项包含 action、target、request、result、applied。核心要求动作、目标一致，result=approved 且 applied=true；旧 approved、冻结批准和普通回答均不放行。授权的核实记录与中心 execution 结果分开保存。冻结路径关口已删除；无订阅候选且缺按量授权能力时卡住，不发车间自己的卡。

流程把原申请、动作、目标和检查点先落盘，再通过中心自己的身份客户端只读查询。issue 执行等待结束模型轮，程序按五分钟回查；status/why 的原因和下一步包含原申请号。中心结果不明继续等，拒绝/过期阻断。集群批次从 production.json 认固定 revision，只核对原申请的 operation_id、operation_matches、Succeeded 与同步后健康结果；原同步进程退出不重跑同步脚本。核实器目前只支持 argocd/sync_app，不支持的授权类别不放行。

亲眼看许可 scope 为 `contract:<活>:<合并提交>`。basis 保存三段约定，delivery 保存当前版本与文本；等待引用含同一 delivery/version。飞书通道只认 Kun 的 open_id、配置的私聊及引用原送达的回复；旧版本被 superseded，旧送达回复不能回答新版本。报告许可为 `report:<目标>:<报告号>`，payload 只有 HTML 路径、散列和原报告幂等键。私聊报告反馈仍回源核验身份，再按报告快照归件，未答不算同意。

飞书 transport 在外部调用前持久记 started；发送响应丢失只查原私聊消息，没找到也记 unknown。已有报告旧日志带原 message_id 或 started 时先对账。报告不发附加摘要。`reply` 是同一通道的只读回复查询；send/reconcile 的一次送达协议不变。

上线后 `verify_intervention_live.py` 的 no-approval-cards、authorization、deliveries、service 均只读现役事实、规则、送达库及进程版本；不需要 GitHub 或授权中心凭据。业务隔离回放见 `scripts/verify_intervention_business.py`。
