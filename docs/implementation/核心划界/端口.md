## 核心里因为没有端口才写在核心的职责

找法：在核心里找做的是「只属于一个通道、一类活、一种交互」的事（N1），或者核心替插件做、只因为插件没有地方交给核心的事；再加上介入点实施单（#173–#175）要往核心里加、要用插件配合的事，标「还没写」。

三种结论：**并进现有端口**指在现有端口上加方法或字段，由插件做；**删掉**指按介入点裁决这件事不再做，所以也不需要端口；**留核心**指它本来就命中「只能放核心」的判据，缺的不是端口。

### K12 总览认 GitHub 的资料字段

`origin` 从活的资料里取 `title`、`html_url`、`repo`、`number`，再从正文里取第一行引用当 Kun 的原话（`src/workshop/reports/report.py:19-29`）。这些是 GitHub 上一个 issue 的字段；#181 把它交给本单（`给人看的部分.md` 末节）。G3 已把它随 `report.py` 移出核心，不再违反 R22，但查看工具仍只认得 GitHub，换一种来源就取不到标题和链接。

结论：流程端口加一个可选方法，给一件活的标题、链接、简称和原话；查看工具调它，没实现或出错时不显示来源。理由：

- 资料的格式是来源定的，一个流程知道自己接的是哪种来源；查看工具已经用同样的办法调流程的 `describe`（`src/workshop/reports/report.py:140`，查看工具拿装配层传进来的注册表，`给人看的部分.md`「落点」一节）。
- 不放进来源端口：一件活的资料可能来自几个来源（`Event.source` 每条不同，`models.py:37`），来源端口不认识活。
- 不放进 `Event` 的字段：`Event` 已有 `title`（`models.py:41`），加链接要改值类型和事实格式；原话那一行是 issue 写法的约定，不该让核心存。

### K13 项目经理

裁决：核心管卡住活的项目经理，外部看门管全局空闲和系统故障；一件活最多一个项目经理，新情况交原会话；项目经理不占普通执行位（交接页「项目经理」，介入点 R11）。

- **给在跑的会话送新情况**：执行者端口没有这个方法。`resume` 是在上一轮退出之后接回同一个会话（`ports.py:98-99`），不是给正在跑的会话送话；实现里交互的 Orca 终端和非交互的子进程两条路都只有起和停（`plugins/executors/local/adapters.py:177-189`、`:290-299`），没有往在跑的会话里送话。#175 标准 3 要「新情况可靠投递给它」，所以执行者端口要加一个可选方法，方法名由 #175 定。
- **事项归属、去重、接管**：裁决是核心管单件、看门管全局空闲和系统故障，双方共享事项归属与去重，核心失效时看门接管（交接页「项目经理」，#175 标准 1）。这是核心和看门两个进程之间的约定，不是插件端口；记在哪、谁写，由 #175 定。项目经理不占普通执行位，这一点由核心分名额时守（J3）。
- **看门那一路**：核心失效时看门要起项目经理（#175 标准 1）。看门现在用系统 Python 只跑 `watch/__init__.py`（`scripts/launch_agents.py:31`），合约也禁止它引用插件（`pyproject.toml:63-67`），按现在的装法它拿不到执行者插件。看门怎么起项目经理（另一条独立入口，还是经别的进程转一手）由 #175 定，引用归属见 #182；记在这里免得以为执行者端口一定能两边共用。

### K14 全车间优先级

裁决：全车间可开工的活按 P0、P1、P2，同级先到先做，缺省 P1；只在派新一轮时排（交接页「自动接单与排序」，介入点 R2、R4）。

### K15 业务在跑的计数：留核心，判空闲归看门

介入点 R11 要「agent 和程序作业连续 5 分钟都没有在跑」就启动项目经理。现在心跳的 `active` 是 `engine.occupied()`，只数没停的轮（`beat.py:228`、`engine.py:269-270`），程序作业不算；裁决写明不能用它判空闲（交接页「现有实现最容易漏掉的地方」）。裁决是外部看门管全局空闲（交接页「项目经理」，#175 标准 1–2），所以「连续 5 分钟没在跑」由看门判。看门要的是一个对的计数：真正推进活的 agent 轮和程序作业算，轮询、看门、项目经理不算。轮和作业都是核心的记录（作业由核心的 `Jobs` 管，类在 `jobs.py:158`，守护进程在 `src/workshop/cli.py:183` 建它），谁在跑只有核心知道（J1），计数由核心写出来（例如写进心跳）给看门读。两边都不用问插件，不需要插件端口，由 #175 做。

### K16 等待端口配置的字段校验

核心校验每个等待端口的配置必须有非空 `endpoint`、`timeout` 在 0 到 30 秒（`rules.py:30-34`）。核心自己不读这两个字段：它只把整段配置原样传给插件（`waits.py:69`、`:74`、`:80`），用的是插件（`plugins/intervention/client.py:33`、`:36`）。收窄后的 J6 说「核心原样转交的内容，格式由收的一方定、收的一方校验」，这一段应该由插件校验。

结论：等待端口加一个可选 `validate(config)`，装配层启动时调，做法同驱动的 `validate`（`src/workshop/registry.py:39`）；核心只查 `wait_services` 是「名字 → 对象」。启动时校验的分工见 Kun 定的第 4 件。

## 介入点要用的端口

### 交接页已定的（照抄）

- 核心只保留通用暂停、恢复与事件端口，保存不透明等待引用和暂停位置；业务流程经核心端口调用插件，插件之间不互引；规则只有 `rules/workshop.yaml` 一份。
- 核心与插件先落记录再确认，用稳定操作号重试和对账；插件不可用时保留暂停；超时不是批准，重复回答不能重复执行。
- 外部入口不依赖坏掉的车间环境或状态库；发送不可用就持久保存，恢复后对账，不绕过许可另发通知。
- 具体表名、端口名、序列化格式由实施确定，不得因此改动等待权威归属、批准边界或打扰次数。

## 只读入口算不算端口
