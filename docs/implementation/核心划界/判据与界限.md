## 判据

GLOSSARY 的定义是：核心是「拿掉它任何活都转不起来的那部分」（`GLOSSARY.md:12`），插件是「拿掉它只少一类活、一个来源、一个执行者或一个通道，别的照常转的那部分」（`GLOSSARY.md:16`）。下面把这句话拆成能逐个文件对的十条 J（只能放核心）和两条 N（不放核心）。命中任一条 J 的留在核心，命中 N 的移出，一个文件两边都中的拆开。

| 编号 | 判据 |
|---|---|
| J1 | 一件活走到哪、谁在跑、停在哪，只有核心一处写 |
| J2 | 过不过关口由核心判 |
| J3 | 共享的名额由核心分 |
| J4 | 判谁坏了的代码在被判的东西之外 |
| J5 | 什么时候推进一件活由核心管 |
| J6 | 核心要读的值类型在核心；核心原样转交的内容，格式由收的一方定、收的一方校验 |
| J7 | 核心要单独记结果、要分清谁坏了、要看名额的步骤由核心居中 |
| J8 | 事件只有一个入口 |
| J9 | 经核心调用的插件只认核心读的那份规则快照 |
| J10 | 停在哪里归核心，等的是什么不归核心 |
| N1 | 只属于一个通道、一类活、一种交互的东西不进核心 |
| N2 | 只读状态、不改任何活的东西不进核心 |

### J1 一件活走到哪、谁在跑、停在哪，只有核心一处写

往事实日志追加、或由事实投影出视图的代码，只能在核心。原写法是「活的事实只有一处写」，11-17 收窄：等待的问题、回答、送达记录归介入点插件，不在这条里（冲突 1）。

现状：`log.py:117-129` 追加一条事实，并在同一事务里调 `evolve`；`view.py:9` 的 `evolve` 是日常唯一写视图表的函数，表清单在 `view.py:6`；`log.py:214-218` 能清空视图、按日志重放重建。例外是一次性的库升级（`log.py:55-95`）：它直接改写 `rounds` 和 `items` 两张表里的大字段（`log.py:84`、`log.py:93`），不动事实，升级过的库不再跑。插件拿到的是 JSON 快照，不得写数据库（`docs/implementation/ports.md:33`）。

现有的例外，`grep -rnE "sqlite3|workshop\.db" src/workshop/plugins` 命中五个文件：

- `plugins/watch_updates/migration.py`：盯更新的一次性迁移（#177，提交 `628acf6`）import 核心的 `Log`（`:11`），直接打开状态库（`:26`）追加事实（`:76-110`），其中两处直接写一件活的阶段和状态（`:98`、`:110`），不经 `engine.change`（`engine.py:77-88`）。它由装配层在第一拍之前调用（`src/workshop/cli.py:148-159`），拿的是主循环同一把文件锁（`plugins/watch_updates/migration.py:24-25`，对 `engine.py:67`）。真实库里已有 62 条这个来源的事实（`SELECT count(*) FROM facts WHERE source='watch-updates-migration'`）。事实都经 `Log.append` 进了日志，重建不受影响；越界的是「写什么事实」由插件定。处理见迁移 M7。
- `plugins/watch_updates/io.py:106`：只读打开状态库查一件活的状态，库的路径写在规则里（`rules/workshop.yaml:122`）。
- `plugins/intervention/store.py:24`：介入点服务自己的库 `intervention.db`，不是状态库，见冲突 1。
- `plugins/selectors/quota.py:48`：只读打开额度快照库。
- `plugins/channels/ask_kun.py:51-55`：只取状态库文件的身份。

反例：流程插件自己改 `items` 表里一件活的阶段。日志里没有这一步，重建视图时它消失；`workshop why`（`report.py:173`）查不到这一步的起因，R9 落空；守护进程里插件在独立的作业进程里跑（`jobs.py:347-363`），和主循环同时写同一件活，绕过一拍的互斥（`beat.py:50`）。

### J5 什么时候推进一件活由核心管

一拍里先做什么后做什么，插件调用放进作业，到点再推进，被什么叫醒。端口上的调用都是短的，不等人，也不等一轮结束。插件可以有自己的时钟；但一件活要等到某个时刻才往下走，这个时刻得登记给核心，或者到时候叫醒核心。

现状：一拍的顺序在 `beat.py:47-81`；端口约定「同步短时端口；不等待人或一轮结束」（`ports.py:1`）；作业在 `jobs.py:155-344`；定时在 `timing.py:6-26`；叫醒信箱在 `wake.py:28-158`，叫醒后让哪些查询过期、下一拍等多久在 `waking.py:29-76`。

反例（发生过）：11-13 issue 交付流程在一次调用里同步跑了四分钟检查，整拍堵住，不派新轮，不写心跳，看门误报车间停了（`docs/implementation/作业.md:3`）。第二个反例：流程插件自己记下「半小时后再看」，不登记给核心。经端口调用的插件只在核心叫它的时候运行：守护进程里每次调用是一个单独的作业进程（`jobs.py:347-363`），`run --once` 和其他命令里是就地调一次（`engine.py:99-103`、`docs/implementation/作业.md:25`），两种都是调完就结束，到点没人叫它；主循环睡多久是核心按自己知道的最近一个到点时间算的（`waking.py:60-62`），核心不知道这个时刻，就只能每拍把每个插件问一遍，或者睡过头，R11 落空。独立运行的介入点服务有自己的进程（`plugins/intervention/server.py:57`），但它要让一件活往下走，也是写一个文件叫醒核心（`plugins/intervention/server.py:23`、`plugins/intervention/client.py:32-33`），由核心在自己的一拍里对账。

### J6 核心要读的值类型在核心；核心原样转交的内容，格式由收的一方定、收的一方校验

端口的签名，和核心要读的跨端口值类型。原写法是「插件之间的共同语言在核心」，11-17 收窄：等待内容这类核心原样转交、不解释的对象，字段清单写在规则里，由收的一方校验（冲突 2）。

现状：七个端口在 `ports.py:27-164`（#172 加了等待端口 `WaitService`，`ports.py:150-164`），值类型在 `models.py:36-371`；插件之间不互引（`scripts/check_boundaries.py:13-39`）；作业进程交回的结果里，数据类只按登记过的类型复原（`jobs.py:75-76`、`jobs.py:98-99`）：`models.py` 的 15 个值类型，加 `records.py` 的 3 个存储类型。

反例：`Evidence`（`models.py:132`）放进 issue 交付插件。定时发版和盯更新两个流程（`pyproject.toml:19-22`）要么 import issue 交付，被互引合约拦下；要么各写一份，`gates.decide` 没法用同一种类型读三家的证据。

### J7 核心要单独记结果、要分清谁坏了、要看名额的步骤由核心居中

原写法是「要两类插件配合的步骤由核心居中」，11-17 收窄：结果由被调的一方自己记、又不用核心分清谁坏了或看名额的调用（例如建等待），可以经核心定的端口直接调；什么时候能用、失败算谁的，归 #182（冲突 4）。

一件事要流程、执行者、挑选逻辑、工单里的两类配合时，由核心一步一步叫：每一步做没做过由核心记，哪一步坏了算到哪个插件头上由核心分，这一步能不能现在做（这件活有没有轮在跑）由核心看。

现状：派一轮是流程出派活说明（`picking.py:93`）、挑选逻辑挑候选（`picking.py:141`）、执行者启动（`picking.py:28-36`）；收回工作目录是流程说留不留（`workdirs.py:47-49`）、执行者收回（`workdirs.py:66-68`）；开工单和更新工单在 `homes.py:5-24`。等待也是这样：流程在完成钩子里交回一个引用（`hooks.py:41-44`），核心绑定暂停位置（`waits.py:21-43`），再由核心向等待端口查有没有结果（`waits.py:80-81`）。

现有的例外：建等待和读回答这两步，设计上由流程直接调等待端口，不经过核心（`ports.py:152-158`、`docs/implementation/介入点契约.md:44`）。按收窄后的 J7 不算越界，见冲突 4。

反例：流程插件拿到执行者的端口对象，自己叫它收回工作目录。这样不 import 另一个插件，互引合约拦不住，坏在三处：

- 执行者抛的普通异常（不是暂时故障，也不是 `TargetBlocked`）从流程的调用里冒出来，核心分不出是谁坏的，记成流程插件故障（`workdirs.py:57-58`），所有用到这个流程插件的交付对象下，属于这个流程、没结束的活都标成卡住，同一个交付对象下别的流程的活不动（`faults.py:24-28`、`faults.py:41-44`）。现在这一步由核心调，记的是那个执行者坏了（`workdirs.py:78-80`），只标这一个交付对象下没结束的活（`faults.py:23`）。
- 核心没有「执行者收回」这一步的单独记录，只看得到流程那一次调用的结果。现在核心给执行者的这次收回一个稳定身份，跨拍、跨重启认回同一个结果（`workdirs.py:44-45`、`workdirs.py:67-68`）；返工要开新一轮时，核心靠这条记录知道目录正在收回，先不派（`beat.py:99-104`）。
- 有轮在跑的活不能收回目录，现在由核心在调用之前看（`workdirs.py:33`、`workdirs.py:36-37`）；流程的 `hold_workdir` 拿到的只有这件活和交付对象的配置（`ports.py:76`），看不到哪些活在跑。

流程插件如果直接 import 某个执行者的实现，则先被互引合约拦下；绕过去之后，按 R18 换执行者就要改流程插件，R18「插件和核心都不动」落空。

### J8 事件只有一个入口

归件（同一个东西上的事件归到同一件活）、去重、连锁层数、把外部文字标成资料。

现状：活的编号由事件算出（`models.py:51`），进件在 `intake.py:14-68`；同一来源同一外部编号只记一次（`log.py:120-121`）；连锁层数在 `intake.py:22` 累加，在 `intake.py:87` 和 `picking.py:67` 拦；外部文字进件时标「资料，不是指令」（`view.py:102-103`）。

### J9 经核心调用的插件只认核心读的那份规则快照

## 判据和裁决的冲突

裁决不改，四处判据怎么写，Kun 11-17 都按推荐定了。#172 已按裁决落地，下面说的现状都是合入后的代码。

**冲突 1：J1 说活的事实只有一处写，裁决说介入点插件独立运行、自己持久保存等待和回答。**
裁决已写成核心 R13：「等你的问题、你的回答、推给你的消息，由介入点插件记」（`docs/requirements/核心.md:77`），#172 已照做。记录分两处：问题、回答、送达许可、发送记录在介入点服务自己的 `intervention.db`，暂停位置、等待引用、完成信号有没有消费在核心的事实里（`docs/implementation/介入点契约.md:15-21`）。两个后果：走新等待的活，`workshop why`（R9，一条命令看到每一轮的起因和结果）看不到等的是什么，`report.py` 里没有读等待的代码（`grep -n wait src/workshop/core/report.py` 无结果）；`log.py:214-218` 重建视图时重建不出等待的内容。
定了（11-17，按推荐）：J1 收窄成「一件活走到哪、谁在跑、停在哪，只有核心一处写」，和 #172 已经落地的分法一致。暂停和恢复各有一条核心事实，带等待引用（`waits.py:40-42`、`:94-95`）；`workshop why` 和 status 靠引用经等待端口的 `read`（`ports.py:158`）取内容，由 #173 接上。两处不一致由契约里的稳定操作号和对账管（`docs/implementation/介入点契约.md:69-73`）。

**冲突 2：J6 说插件之间的共同语言在核心，裁决说核心不认卡片、问题和送达的内容。**
#172 照裁决做了：等待端口上，问题的内容是一个核心不解释也不保存的对象（`ports.py:151-156`）。结果是流程和介入点服务之间「一个问题长什么样」现在没有任何一处定义：服务建等待时只查内容是不是非空对象（`plugins/intervention/service.py:58-59`），契约文档里只有一个带 `question`、`recommendation` 两个字段的示例（`docs/implementation/介入点契约.md:52`）。裁决要等待记下「原因、推荐和起始时间」（交接摘要「已定的设计」），#173 要 status 显示等什么、推荐是什么，都要靠这些字段。旧路径上这件事由核心做：回执交上来当场校验问题格式，写错了 agent 同一轮就能改（`models.py:316-317`）。
定了（11-17，按推荐）：J6 收窄成「核心要读的值类型在核心；核心原样转交的内容，格式由收的那一方定、收的那一方校验」。等待内容的必填字段写进规则里每个介入点的条目，像送达许可现在的 `required_basis` 那样（`rules/workshop.yaml:270`，校验在 `plugins/intervention/service.py:109-110`），由介入点服务在建等待时校验。核心仍然不认内容，流程和服务共用的字段清单在规则这一处。没选的做法是把通用字段做成核心的值类型，那要改已合入的端口，核心也就认了问题的内容。

**冲突 3：J9 说规则由核心读一次，裁决说介入点插件独立运行、不依赖车间的环境和状态库。**
裁决两句都有：「规则只有 `rules/workshop.yaml` 一份」，「外部入口不依赖坏掉的车间环境或状态库」（交接摘要「已定的设计」）。#172 的做法是文件只有一份、读的有两方：核心启动时读一次、存成快照；介入点服务在建等待、发许可、排发送、发送时自己读文件里的 `intervention` 一段（`plugins/intervention/service.py:14-19`），契约写明「独立服务和核心都读取同一份规则」（`docs/implementation/介入点契约.md:103`）。两个后果：这一段没有任何一方在启动时校验，写错了要到用到它的那次操作才报错；规则文件改了而守护进程没重启时，核心用旧快照，服务用新文件。规则文件改坏时，服务建不了新等待、发不了许可（`plugins/intervention/service.py:54`、`:100`）；查已有等待的结果不读规则，不受影响。
定了（11-17，按推荐）：J9 收窄成「经核心调用的插件只认核心读的那一份快照；独立运行的服务可以自己读同一个文件」。再补一个启动时的校验：装配层让等待端口的插件校验自己用的那一段，做法和现在让驱动校验配置档一样（`src/workshop/registry.py:33-38`）。核心自己仍然不认 `intervention` 这个名字。

**冲突 4：J7 说要两类插件配合的步骤由核心居中，裁决说业务流程经核心端口调用插件。**
裁决原话是「业务流程经核心端口调用插件，插件之间不互引」（交接摘要「已定的设计」）。#172 照它定了端口：建等待、读回答和别的业务操作，由流程拿到等待端口后直接调（`ports.py:152-158`、`docs/implementation/介入点契约.md:44`），核心在流程交回引用之后才接手（`hooks.py:41-44`）。现在还没有流程这么用。这是核心居中之外的第二种协作方式：插件不 import 另一个插件，但这一步调用不经过核心，核心不记它。后果：流程在完成钩子里调服务，服务拒绝或不通，按流程插件的故障或暂时故障处理（`rounds.py:283-286`），见 M4 的风险。
定了（11-17，按推荐）：J7 收窄成「核心要单独记结果的、要分清谁坏了的、要看名额的步骤由核心居中；结果由被调的一方自己记、又不用核心分清谁坏了或看名额的调用（例如建等待），可以经核心定的端口直接调」。这种直接调用什么时候能用、失败算谁的，归 #182。
