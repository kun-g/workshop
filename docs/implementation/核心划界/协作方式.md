1. **靠什么联系**：四样，端口、事件、规则、事实记录。再加一种收窄后的 J7 允许的「经核心定的端口直接调另一方」。共享文件和绕过端口不算联系方式，现有 7 处（插件之间 2 处、插件绕过通道 1 处、插件直接碰核心的文件 4 处）都列为越界。
2. **插件能用核心的什么**：只能 import `workshop.core.models` 和 `workshop.core.ports`。前者是核心要读的值类型（J6），后者是端口签名和端口异常，异常决定核心把故障算到谁头上（J4）。核心里别的模块，要么是核心的机制，插件用了就等于替核心做判断或者摸核心的内部位置；要么已定要迁出核心（卡片、给人看的部分），插件更不该依赖。

## 二、插件能用核心的哪些东西

### 允许清单

| 能用 | 里面是什么 | 理由 |
|---|---|---|
| `workshop.core.models` | 跨端口的值类型（`Event`、`Poll`、`After`、`Evidence`、`Receipt`、`Usage` 等，`core/models.py:36-371`）和三个常量：阶段表 `STAGES`、一轮的结果 `OUTCOMES`、派活说明的默认上限 `DEFAULT_BRIEF_MAX_CHARS`（`core/models.py:10-12`） | J6：核心要读的值类型在核心。插件交回的东西核心要读、要校验，类型只能有一份；作业进程交回结果时也只按登记过的类型复原（`core/jobs.py:78-79`）。 |
| `workshop.core.ports` | 端口签名（`core/ports.py:27-171`）和五个端口异常：`Retryable`、`Unavailable`、`TargetBlocked`、`InputBlocked`、`ChannelRejected`（`core/ports.py:7-24`） | J4：异常就是插件告诉核心「这次失败算谁的、波及多大」的语言。比如 `TargetBlocked` 只波及一个交付对象（`core/faults.py:37-41`），`Retryable` 走退避（`core/faults.py:70-77`）。插件不用它们，核心就只能把所有失败都当插件坏了。 |

`core/__init__.py` 只有一行说明，import 子模块时必然经过它，不单列。

不在清单里的核心模块共 25 个（`core/` 下 28 个 `.py`，减去 `__init__`、`models`、`ports`），理由分两类：

- **核心的机制**（`engine`、`log`、`view`、`gates`、`picking`、`rounds`、`wake`、`waits`、`jobs`、`rules`、`relations` 等，#180 界限表里「留在核心」的那些）：写事实、判关口、分名额、定什么时候推进。插件 import 它们，要么替核心做了判断（J2、J5），要么依赖了核心的内部位置，核心一改插件就坏，R17「核心不用改」反过来也落空。
- **已定要迁出核心的**：`cards` 和 `asking` 的卡片部分，按介入点裁决移到介入点插件。迁走以前还在 `core/` 里，插件 import 了，迁移时就多一处要改。给人看的四个模块（`metrics`、`status_page`、`observe`、`report` 除 `resolve` 以外的部分）已经搬到查看工具 `src/workshop/reports/`（#181 G2–G4，已合入 `067989a`），插件同样不该依赖它（合约第二条）。

清单里两样东西会随介入点迁移变小，但不出清单：`models` 里通道专用的 `Answer`、`ChannelPoll`（`core/models.py:262-277`）和 `ports` 里的 `ChannelRejected`（`core/ports.py:7-8`）跟旧通道端口一起，由 #176 拿掉或改形（端口怎么改见 #183）。

### 清单外、但不是核心的：共用库

插件还 import 三个顶层模块：`workshop.github_identity`（11 个文件）、`workshop.path_policy`（2 个）、`workshop.running`（1 个），共 14 行（`grep -rnE "^\s*(from|import) workshop" src/workshop/plugins --include='*.py' | grep -vE ":\s*(from|import) workshop\.(core|plugins)"`）。它们不在 `core/`，也不是插件：GitHub App 身份、哪些路径不用上线、守护进程在跑的版本，几个插件都要用。它们只 import 标准库和 `core.ports`（`src/workshop/github_identity.py:13`），不 import 任何插件。

定了把它们算「共用库」（Kun 11-18，末节第 2 件）：插件可以用，但共用库不许 import 插件（合约草稿第三条）。共用库不算核心，R19「核心改了多少行」不数它们；它们也不能长出「替某个插件做判断」的代码，否则就该搬进那个插件。

## 三、插件之间

### 规矩

一个插件不能 import 另一个插件，包括它的常量和类型；要合作只经第一节的四种方式，或第五节的直接调用。一个插件包内部的文件互相 import 不受限。这条已写在车间 `AGENTS.md:12`，机器已经在拦：`scripts/check_boundaries.py:13-39` 按 `plugins/` 的目录每次生成一条 import-linter 的 independence 合约（各模块之间直接、间接都不能互相 import），本次在 `067989a` 上跑 `scripts/check.sh` 输出「插件之间不互引 KEPT」。开单时说「反方向没有约束」只对插件→核心成立，插件→插件已有约束。

理由：插件互引，按 R18 换掉被引用的那个插件时，引用方也要改；拿掉一个插件，引用它的那个也坏，违反插件的定义「拿掉它只少一类活……别的照常转」（`GLOSSARY.md:16`）。

## 五、不经核心的直接调用

收窄后的 J7：「核心要单独记结果的、要分清谁坏了的、要看名额的步骤由核心居中；结果由被调的一方自己记、又不用核心分清谁坏了或看名额的调用（例如建等待），可以经核心定的端口直接调」（`判据与界限.md:122-124`）。这一节把「什么时候能用」「失败算谁的」写成可以逐条对的规矩。

### 什么时候能用

五条同时满足才能用，缺一条就由核心居中：

1. **被调方自己持久记结果**，并且用调用方给的稳定操作号做幂等：同号重试拿回原结果，不重做。等待端口的 `create` 就是这样（`core/ports.py:162-164`，服务端操作表见 `docs/implementation/介入点契约.md:15-21`）。核心因此不用为这一步单独记事实。
2. **核心不用分清谁坏了**：被调方失败只影响调用方手上这一件活，不需要核心把被调方隔离、也不需要波及被调方的其他用户。
3. **不占名额**：不开会话、不占并发位、不碰串行路径（J3 管的那些）。会占名额的，例如收回工作目录要先看这件活有没有轮在跑（`core/workdirs.py:33-37`），必须核心居中。
4. **经核心定的端口，对象由核心交给调用方**：被调方实现的是 `core/ports.py` 里的某个端口，调用方拿到的是装配好的端口对象，不 import 被调方的模块，也不在插件里自己按入口点加载别的插件。流程拿等待端口的做法：核心调 `after` 时传只读句柄，按 `wait_services` 的名字给出等待端口和配置（[端口.md](端口.md) D3，随 #173 落实）。不能靠装配层把端口交给流程实例：插件由无参工厂构造（`docs/implementation/ports.md:7`），守护进程里每次调用还在单独的作业进程里（`docs/implementation/ports.md:9`）。
5. **只在流程的完成钩子 `after` 里调，而且是短的**：不另起线程或后台轮询（J5，`core/ports.py:1`）。限定在完成钩子，是因为下面的失败表靠 `After` 的返回值把失败收在这一件活里；`assess` 要交回 `Evidence`、`classify` 时活可能还没建，都没有对应的写法，以后真要在别的端口方法里直接调，先给那个方法补失败的交回方式（现在不先加，真要用时随那个需要一起定，见 [端口.md](端口.md)「#182 交来的端口问题」）。结果要影响活的走向，必须经调用方的返回值交回核心，例如建好等待后把引用放进 `After.wait`（`core/models.py:138`），由核心绑定暂停位置（`core/hooks.py:41-45`、`core/waits.py:21-43`）。

### 失败算谁的

核心只看得到它叫调用方的那一次，所以**失败算调用方的**。调用方必须把被调方的失败翻译成只影响这一件活的结果，不能让被调方的异常原样冒出来：

| 被调方的情况 | 调用方怎么交回 | 核心怎么处理 |
|---|---|---|
| 明确拒绝（内容不合格、规则不允许） | `After(blocked=原因, next=下一步)`；`next` 必须非空，否则核心按协议错误拒收、记成流程故障（`core/hooks.py:21-23`） | 只把这件活标卡住（`core/hooks.py:96-99`），别的活不动；卡住后由项目经理处理（介入点 R11，由 #175 落实）。 |
| 暂时不通（服务没起、超时、连不上） | `After(pending=True, reason=…, next=…, recheck_after=…)` | 这件活进「定时」，按退避重查（`core/hooks.py:78-83`）；连续到 `pending_limit`（默认 5，`core/hooks.py:69`）才把这一件标卡住。 |
| 调用方自己的错（参数拼错、没接住的异常） | 照常抛出 | 按流程插件故障处理（`core/hooks.py:110-111`），这是调用方该修的 bug。 |

暂时不通时不抛 `Retryable`：那样核心按这个流程的暂时故障退避，连续三次就把整个流程判坏（`core/hooks.py:108-109`、`core/faults.py:75-76`），所有交付对象下这个流程没结束的活都标卡住（`core/faults.py:35-58`）。被调方不通就停掉调用方的全部活，等于核心又要分清谁坏了，和第 2 条矛盾，也和介入点契约「插件退出、拒绝请求、超时……活保持暂停；记录故障类型，不隔离别的活」（`docs/implementation/介入点契约.md:74`）的意思不一致。Kun 11-18 定了按上表交回（末节第 3 件）。

另一个要守住的点（#180 M4 的风险）：问题写错了要能当轮退回给 agent 改。按上表它会落在「明确拒绝」那一行，活卡住而不是当轮退回；怎么当轮退回由 #173 接线时定。
