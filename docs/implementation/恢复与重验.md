# 卡住、恢复与重验

`workshop status` 的「等回答的问卡」列出需要 Kun 判断的事；「卡住清单」交给项目经理处理工具、权限、流程或等待次数的问题。`notices: hold` 只压住通知，问卡仍发送。不能用一条通知代替问卡，也不能伪造回答来恢复。

执行者遇到操作阻塞时交 `outcome=nothing`、不带 `advance`，在 `evidence` 的 `issue-delivery/v1` JSON 中写：

```json
{"schema":"issue-delivery/v1","blocked":{"reason":"缺少 promtool","next":"项目经理安装后恢复"}}
```

核心保存原因、建议动作和归项目经理的工序，状态为卡住；没有有效问卡的旧版 `leave.kind=等你` 也转为卡住。需要 Kun 定范围或授权时，用有选项、推荐和理由的 `ask`。已拒收或作废的问题属于通道阻塞，不算等回答。

## 返工恢复

```sh
workshop recover 'gc#109' --mode rework --reason '外部依赖已恢复，需要重新执行' --quote 'Kun 在会话里的原话'
```

`--reason`、`--quote` 都必填且不能空白。保留历史，追加恢复事实，由现有返工逻辑回执行；没有登记检查的活先回接单核对（issue 交付；旧流程是说清楚）。不会替代交付审批或绕过其他关口。完成、正在跑一轮、已登记返工或插件仍隔离的活不能用此命令恢复。

## 原阶段续等

```sh
workshop recover 'gc#109' --mode wait --reason '部署依赖已完成，继续核对上线'
```

仅用于阶段完成钩子的等待达到 `pending_limit` 后卡住、且可以继续自动回查的活。保留原阶段、回执和幂等标识，重置本次等待次数；取原流程建议和从五分钟开始的指数退避中较晚者继续回查。不重新发版，也不退回执行。新的等待批次有新的定时及作业身份；再次达到上限仍卡住。旧版没保存回查入口时，从该阶段已结束轮与完成钩子的事实重建；找不到可靠入口则报错，不能猜。

## 追加一次验收

issue 交付从 ws#215 起没有验收阶段，不再提供这条路（`prepare_recovery` 已删，命令会答「本流程不支持追加核验」）；两段 DoD 由程序在交付时查，退回超限用上面的返工恢复。下面是核心仍保留的通用机制，供以后有验收阶段的流程用。

```sh
workshop recover 'ws#62' --mode verify --reason '验收环境已修复'
workshop recover 'ws#62' --mode verify --reason 'main 已合入检查修复' --ref main
```

第一种仍验原交付提交；第二种先解析当时的 main 为完整提交号，并验证它包含本活最近的合并提交。命令固定这个提交，之后 main 移动不改变本次检查对象。

只对到过验收、原交付已完成、尚未验收通过且没有打开的 PR 的活提供机会。一次命令给一次机会；尚未消费时不可叠加。命令追加核心恢复事实，随后沿执行阶段的 `rerun_acceptance` 请求进入验收，由流程完成钩子幂等消费。已用过的次数与机会历史保留，不清空状态文件。

验收者收到固定检查提交的只读副本，`acceptance.head` 填派活说明的检查提交。原合并提交仍是交付身份；流程检查必须成功，另一个执行者仍按验收步骤判断，有亲眼看要求时仍等问卡。使用 main 的检查结果不能替代原交付的生产核对。

`workshop why 'ws#62'` 可看到恢复原因、Kun 原话（返工）、计划中的原交付/固定检查提交、消费机会及验收核对。命令验证失败不改这件活；不会删除历史事实。

实现边界：核心提供 `recover`、阻塞字段与事实；流程可选 `prepare_recovery(item, options, target)` 只读返回业务计划，由核心保存。提交关系与重验次数只由 issue 交付插件解释。没有新增依赖或配置副本。
