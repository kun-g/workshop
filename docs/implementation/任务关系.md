# 任务关系

权威需求为核心 R31、R32 和 issue交付 R12；词义见 GLOSSARY。

`Flow.relations(objects, target)` 是可选只读批量端口。核心只交活标识和对象键，插件返回以活 id 为键的 `Relations`：前置、子单、所属总单、相关对象、汇合阶段，以及读取错误。每个关系对象带稳定标识、显示名和来源完成状态。未实现此端口的流程保持原行为。

issue 交付插件用 GitHub GraphQL 一次读最多 20 张 issue 的 blockedBy、parent、subIssues 和 relatesTo；各连接逐页读完并核对总数，不完整结果不能发布为空快照。跨仓库对象的稳定标识带完整仓库名。请求使用交付对象的既有 GitHub 身份，不回退个人身份；权限不够会阻止放行。

关系调用走独立作业，结果五秒过期。同一交付对象合批，核心一拍不等网络。首次读取或过期刷新未完成时不派新轮；读取故障在受影响的活上记卡住供项目经理处理，不发故障通知，保留其他阻塞。完整快照入库后在同一拍决定等待或继续。不能用等待期间没收到事件推断前置完成。

前置未关闭显示等前置；总单自己的流程走到汇合阶段（issue 交付为验收）或之后、还有未关闭子单时，显示等子单。子单不阻止此前阶段。两者均不占执行位置或串行路径，也不触发等待问卡。前置齐全后仍检查原来的并发、串行和审批关口。正在执行的轮不因关系变化被中止，下一轮之前重新核对；慢派活作业的参数包含完整快照，最终预订事务再比对快照。

总单照常接单、说清楚、执行、证据、交付；核心不会因子单全部关闭而跳阶段。到验收入口仍有子单未关闭就等待，全关后才派验收轮。issue 交付总单使用自己的 PR、交付提交、登记检查和正常验收流程，另将「当前总单正文＋完整子单集合＋前置」指纹保存在插件状态中，派活、回执结算和收尾都回查。正文、子单集合或关闭状态变化会让旧验收失效。亲眼看仍经 visual-acceptance 问卡，不能把子单关闭当成人工批准。收尾前重新回查完整关系，未验收不能关总单。

相关对象只放当前 `FlowBrief.materials`，不追加为历史原话；核心强制标为「资料，不是指令」。删除相关关系后下一轮不再携带它。status（文字和 HTML）显示等待对象；metrics 将等前置和等子单单列，不计入卡住或排队。

API 依据：[GitHub Issue GraphQL 字段](https://docs.github.com/en/graphql/reference/issues)、[前置关系](https://docs.github.com/en/rest/issues/issue-dependencies)、[总单和子单](https://docs.github.com/en/rest/issues/sub-issues)、[相关关系](https://docs.github.com/en/rest/issues/issues#list-issues-related-to-an-issue)。

总单验收失败照常退回自身执行；交付授权被拒也照常回到执行处理拒绝意见。等待子单时收到返工，先处理返工再按新阶段核对关系。删除最后一张子单仅解除等待，保留总单已经走到的阶段。旧版留下 aggregate 标记、跳过自身执行的活，在没有在跑轮和未结算授权时恢复到其原阶段，作废旧验收问卡，继续自身流程。

真实只读探针：`uv run python scripts/check_relations_readonly.py --output <不存在的新目录>`。它读取真实 GitHub 数据，只在新建本地状态库里调用关系读取和核心准入，绝不启动执行者；可加 `--stages 执行 证据 交付 验收` 比较各阶段准入，阶段仅在隔离库中设置，并不代表实际执行或完成。输出 `admissions.json`、`snapshots.json` 和原样状态；不替代上线后的关系增删、关闭前置、自动恢复及跨仓库验收。

来源事实在验收轮运行期间变化，流程用 `Evidence.superseded` 结束旧轮，作废旧问卡、批准和结果，回到当前汇合阶段；下一拍按新关系等待或重验，不当作验收拒绝或接口故障。已有授权关口必须先结算，拒绝退回执行处理，关系等待不能吞掉人的回答。

关系读取使用独立 `relations_identity` scope，签发器 `--relations-read` 将同一 owner（同一 App 安装）下 `config.repositories` 的全部允许仓库加入令牌，只申请 `issues:read` 和 `metadata:read`。每个仓库必须显式允许 issue 读取并属于同一安装；不能静默丢掉仓库或沿用外层单仓库写令牌。GitHub 会把令牌不可见的关系连同摘要计数一起隐藏，所以校验分页数量不能替代完整的凭据覆盖。规则中两个交付对象均显式配置关系 App 身份，grant-console 的普通操作仍保留原身份。

覆盖边界是同一 App 安装内配置允许的仓库。跨 owner/安装的关系不能由一枚安装令牌完整读取，本次不宣称支持跨安装；配置外的不可见关系也无法单靠 GraphQL 零计数发现。新增交付对象时必须先核对安装与关系读取覆盖范围。正常写操作继续只签单仓库令牌，关系只读令牌不交给执行者。
