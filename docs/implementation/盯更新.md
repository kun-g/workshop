# 盯更新

依据 [盯更新需求](../requirements/盯更新.md) R1–R25、C1–C5。`watch_updates` 是一个插件包，提供来源和流程两个端口；没有核心改动，也不引用其他插件。上游、清单和反馈都是资料。

## 数据和阶段

| 活 | agent 阶段 | 程序负责 | 等待 |
|---|---|---|---|
| 每周对账 | 说清楚：只读本机、仓库、Dokploy 和升级记录、补需要，交结构化提案 | 校验范围、保存快照、提交清单与台账、出周报 | 来源失败、单处版本不明及人工上游写盲区 |
| 一个软件的一个新版本 | 执行：对照需要、方向、画像逐处判断服务端，agent 由程序继承 | 去重、汇成日报/周报、处理反馈 | 验收阶段的下一步显示“等反馈”或“待升级” |

核心阶段固定不变。`After.pending` 七天回查不占 agent；每周来源为未完成版本发一个稳定标识的唤醒事件，重新开始等待周期，执行阶段复用判断。明确“判错了”、部署角色变化，或旧判断迁移到新版格式时重新判断。这样不靠无限大等待上限，也不为每个版本发问卡。

日报和周报等待同批新版本判断汇齐，有紧急或重要项才出日报。规则中的汇齐期限默认一小时，期限后将未完成判断列成盲区，防止一个卡住的软件挡住其他结论；迟到的紧急或重要项当天补报。普通项进入下一份周报。周报包含未反馈项、清单变化、盲区及需要台账的新条目。报告以日期及必要的补报标识固定编号并保存，不用新正文覆盖已发附件；迟到反馈按原报告的快照验证。

## 配置与上线衔接

所有路径、日历、执行者和飞书身份在 `rules/workshop.yaml`。初始 `enabled: false`：原来的 45 项清单是调研格式，含说明性版本命令和字符串形式的过滤条件，不能直接执行。按 issue #102 的分工，项目经理转换 workspace 文件、登记 `contexts/WORKSPACE.md`、停用 version_scan 并更新其 README 后启用；此 PR 不修改那些真实文件。

转换时保留每条使用证据、实际部署位置、日期、备注，重新确认是否属于 R3；不要执行原文件中的 shell 字符串。跟随服务部署的组件并回服务，不能独立共用的不要单列。源文件的 `ours` 转成逐处 `instances`；上游 URL 转成下表对应的对象；`prerelease` 转为布尔值；`tag_filter` 只保留合法正则。tag 带前后缀时（`docker-v29.9.3`、`dsh-v0.2.2`、GitLab 的 `v19.5.3-ee`），`tag_pattern` 用命名组 `(?P<version>…)` 圈出版本号，后缀不再被当成预发布；没有命名组时整个 tag 按 `v` 或 `名字@` 前缀解析。不能明确转的条目列成盲区，不猜。

| 上游 | `upstream` 配置 | 行为 |
|---|---|---|
| GitHub Releases | `{"kind":"github_releases","repo":"owner/repo"}` | 每页 30 条按创建时间倒序读，读到不新于在用最低版本的发布即停，总预算 180 秒。大仓库每页 100 条时 GitHub 十秒内答不出（openai/codex 实测 504） |
| GitHub tags | `{"kind":"github_tags","repo":"owner/repo"}` | 分页读取 tag，按同一版本规则过滤；明确标注缺少发布说明，不编造变化 |
| GitLab Releases | `{"kind":"gitlab_releases","project":"group/subgroup/project"}` | 只读 gitlab.com 公开 API，可用数字项目 ID 字符串；分页保留描述和原文链接，不携带凭据 |
| GitLab tags | `{"kind":"gitlab_tags","project":"group/project"}` | releases 接口不开放时用（`gitlab-org/gitlab` 的 releases 返回 403）。按版本倒序分页，读到不新于在用最低版本的 tag 就停；tag 带发布时取其说明，否则标明缺少发布说明 |
| 无查询接口 | `{"kind":"manual","reason":"没有公开版本接口，须人工核对"}` | 每日跳过；每周即使没有更新也在盲区列出名称、部署和原因，不生成失败活 |

旧清单的 `"upstream":"owner/repo"` 仍按 GitHub Releases 解释。只发 tag 的仓库显式改用 `github_tags`。`manual` 不需要 `tag_pattern/prerelease`，在用版本保留实读字符串、不强行转成语义版本号。GitLab 请求分页总预算 90 秒、最多 100 页，未读全时按失败处理，不把部分结果冒充完整发布范围。接口依据：[GitHub tags](https://docs.github.com/en/rest/repos/repos#list-repository-tags)、[GitLab releases](https://docs.gitlab.com/api/releases/)。

需要台账位于 workspace 一级的 `needs.yaml`，其他流程可以读取，不藏在盯更新目录里。它与清单、来源登记、快照都由同一个 workspace git 仓库跟踪。提交仅包含本次列明文件，不带入别人的暂存改动。报告及插件运行状态放在私有状态目录，不提交到公开仓库。

清单最小格式（软件 ID 和部署 ID 稳定，不用展示名作归件键）：

```json
{
  "schema": "watch-updates/v1",
  "excluded": {},
  "software": [{
    "id": "dsh", "name": "DSH", "kind": "agent", "source": "local",
    "upstream": {"kind":"github_releases","repo":"deepseek-ai/deepseek-harness"}, "prerelease": true,
    "tag_pattern": "v[0-9]+\\.[0-9]+\\.[0-9]+(?:-rc\\.[0-9]+)?",
    "operated_by_us": true, "evidence": "本机安装且正在使用",
    "instances": [{"id":"mac","host":"Mac","service":"dsh",
      "role":"server","version":"0.2.0","read_at":"2026-11-14T01:00:00+00:00","evidence":"只读版本命令及原样输出"}],
    "profile":{"exposed":false,"data":"本地会话","users":["Kun"],"paired":[]},
    "notes":[]
  }]
}
```

未知版本填写 `version: unknown` 和 `error`；不要把镜像日期作为版本号比较。`auto_updates`、`business_image`、`lock_dependency`、`bundled_with` 任一为真，该软件不加入清单。退出时显式提供卸载证据，不能根据未出现在本轮输入就删除。

计算发布范围时只用版本已知的部署；未知部署保留在清单和报告中，由程序补成「版本不明」及原始错误原因，模型给它的升级结论不采用。没有新版本时，未知部署仍在周报盲区显示。仅当一个自动查询的软件所有部署版本都不明时，下一次每日查询记失败，同一原因只生成一次。`manual` 不走这条失败路径。

来源登记是描述性资料，不是可执行配置。例如：

```json
{"sources":[
  {"id":"local","where":"本机包管理、Applications、浏览器历史中的主机名"},
  {"id":"servers","where":"部署仓库及 Dokploy（dc1）的实例登记，不登录服务器"},
  {"id":"clusters","where":"部署仓库的 Application 和 values 声明，不调用 kubectl"},
  {"id":"needs","where":"会话记录、各项目 pm.md、闪念本、Kun 所在飞书群和公司 GitLab issue；只读"}
]}
```

每周对账的执行者逐个给出 `id/ok/evidence`，漏掉已有来源即校验失败；新增来源通过 `source_definitions` 交回并提交。需要格式为 `{"needs":[{"id":"稳定编号","owner":"Kun/agent/同事","source":"可回查出处","statement":"需要什么或碰到什么问题","state":"open","confirmed":false}]}`。`state=met` 必须附 `fulfillment`。新需要由周报点选确认，未确认的下周继续。

新版本事件只带版本号、链接和正文长度；发布说明正文由来源写进私有状态目录 `notes/<活的键>/`，每个版本一个 Markdown 文件，判断时执行者用 rg 搜索后细读。首跑时 n8n、NetBird 一件活的说明超过 400 万字，codex 单次输入上限约 105 万字，正文放进派活说明行不通。执行者的工作目录（`collector/`、`reader/`）初始化成 git 仓库，codex exec 不在 git 仓库里会拒绝启动。

每日判断使用断网只读执行者和清除部署凭据的 `FlowBrief.readonly`；每日来源只读上游与本地快照，没有取机器版本的命令。每周对账使用独立 `watch-inventory` 配置档，在私有状态目录的 `collector/` 中运行 workspace-write sandbox，显式允许网络；可写范围不包含 workspace 数据仓库，清单和台账只能由流程程序写入。对账执行者只交结构化提案，禁止 ssh/kubectl 及其他远程执行，仅读下述登记来源。该 sandbox 不是远端命令过滤器；边界和迁移见“不登录机器的每周对账”。

## 报告与判断格式

以 Kun 认可的 `report-sample.html` 为排版标准。`headline` 是先说原因的一句话（最多 40 字，不含换行或 profile/need/direction 字段名）；`points` 最多三条 `{version,text}`，版本必须对应本次实际发布记录且有 HTTPS 原文链接。`references`、`signals`、`links` 继续校验紧急程度和依据，不显示给人。`features.summary` 自身写清功能与哪件在做的事有关，没有新功能就省略。

每处 `role` 必填 `server` 或 `agent`。server 指独立判断和操作的主体，包括独立安装的工具；agent 指跟随服务端的客户端或节点组件，不等于软件的 `kind=agent`（agent 工具分类）。Teleport、NetBird 要由对账证据确认两种部署，不能从主机数或容器数推测角色。只要求执行者交已知版本 server 的判断，程序忽略执行者自行填的 agent 结论、继承服务端结论并补升级顺序；多个服务端按最高结论和优先级汇总，页面保留不同的逐处结论。没有服务端或有服务端版本不明时，不推测 agent 应升到哪版，先补服务端版本。未知部署仍列折叠盲区，不妨碍其余已知服务端判断。

同一软件的未完成版本在报告里合成一张卡，采用最新版本判断；一个部署的反馈同时落到这些未完成版本。组成员和 id 映射保存在报告的 `feedback_targets`，后来清单新增的部署不会被旧报告选中。软件间部署 id 重名时加软件 id 前缀，页面负责输出准确 id，无需人拼。

旧判断没有 `watch-judgment/v2` 标记，不能当新版短标题渲染；下一次成功对账补齐角色后为未完成的版本发重判事件。旧清单仍可读取，但新对账提案和新判断必须有角色。角色不明的来源先补对账，不给旧实例默认猜 server。启用前项目经理应完成清单角色迁移，再让待办重判；现有 `enabled: false` 保持不变。报告编号加 `-v2`，旧附件不覆盖，旧反馈格式拒绝；该格式从未有用户使用，无需迁移旧反馈。

## 反馈入口

HTML 离线可用，无外部脚本；按按钮选择后复制可读文字和一段 JSON。只有 JSON 中明确选的项生效，未选项保留等待。server 逐处选择，agent 按软件成组。备注仅在「升」「判错了」时输出；正文、备注和链接均不会执行。新功能的“想用”只记台账，不等同“升”。

```text
- Teleport · agent（全部）：升（周末处理）
还有 3 项没选，下周接着问。
```
```json
{"report":"wu-weekly-2026-11-16-v2","items":[{"id":"teleport-agents","choice":"升","note":"周末处理"}]}
```

复制时 JSON 由单个 json 代码块包围；解析也接受纯 JSON。未知报告、未知 id、重复 id、重复覆盖部署、非法选项和旧 schema 都拒绝。需要台账和新功能沿用同一 items 结构，id 也由报告生成，选项分别为「确认/不要了」和「想用/用不上」。

Ash 私聊转发属于工作台，由项目经理接线。本插件接核心标准事件：

```json
{"source":"feishu","ext_id":"om_真实消息号","target":"workshop","object_key":"报告反馈","title":"Kun 的盯更新反馈","body":{}}
```

用 `workshop event --file <文件>` 注入。CLI 自动加 `cli:` 前缀；正文中自报身份无效。插件按消息号回查飞书，验证发送者是规则里的 Kun，取上游原文并核对报告编号。一次反馈可包含多个版本；先归到报告所属的活，幂等保存后由来源把每项送回各自的活。直接说“盯一下 X”或“X 不用了”会启动一次补充对账，补清单同时补感知来源。

文本和 HTML 附件分别通过配置的 lark bot 私聊发送，各有持久发送记录和稳定幂等键。每条成功后落盘，部分失败不会重发已确认消息；进程崩溃造成发送结果不明且超过服务端一小时幂等窗口时停止自动重发，要求核对发送记录。报告没有公共 URL。

飞书只发 HTML 附件（R14，11-15 起不再发逐行文字摘要）；`summary` 仍生成并存进报告记录，供项目经理核对。人工上游、版本缺失和来源失败的详细原因在附件折叠区；原文通过要点版本号链接查看。

## 检查与边界

`uv run pytest tests/test_watch_updates.py tests/test_watch_report.py -q` 覆盖版本过滤与累计发布记录、范围/卸载/失败来源保留、日报条件、周报与逐处报告、反馈重判、停止盯、台账、发送去重及等待。合并前仍跑 `scripts/check.sh`。

流程设计检查：人只做报告反馈；等待和重放由程序承担；判断交给已有订阅的执行者；状态落盘并有来源出处；输入校验和测试先于真实启用。基线：真实运行尚未测，后续看漏收数、判错比例、日报天数和等反馈天数。首次启用后的清单及判断质量由 Kun 亲眼验收，机器测试不能替代。

本期不升级、不改远端配置、不重启、不替同事回复。新增依赖为零。

## 判断规格、隔离预览与人工补发

`model.py` 的枚举、长度常量和 `judgment_sources` 是判断字段规格的来源；校验器及 `judgment_spec` 生成的派活说明共同读取。`brief.judgment_brief` 同时供正式执行和预览使用，不附旧 judgment；仍保留软件画像、需要、方向、发布说明和 correction 原话。不要在 Flow 或命令里另写一份取值表。

### 真实状态预览（不发送）

从仓库根运行。先只读查看配置中 `watch_updates.state_dir/state.json` 的 `versions` 键，选择 1–2 个待查看版本。`--version` 必须用完整键；不要只填软件名。下面两个键是输入占位符，替换为刚读到的键，第二个也可以省略。

```sh
uv run python -m workshop.plugins.watch_updates prepare-preview \
  --rules rules/workshop.yaml --target workshop \
  --version '<版本键一>' --version '<版本键二>' \
  --output .local/watch-preview-20261115
```

输出目录必须尚不存在，不能与正式状态、报告、快照、清单、来源、需要和方向路径重叠。目录权限 0700。命令只读真实输入，按配置时区、小时及周起点计算报告周期，复制所选版本的发布说明，并生成：

- `preview.json`：当时的版本状态、清单、需要台账、方向及时间快照；去掉已发报告和 outbox，所选版本删掉旧 judgment，其他版本保留已有判断作周报背景。
- `<版本键>.brief.txt`：生成的正式判断说明，加标注为资料的本轮输入；`notes/` 指向复制后的发布说明，不从网页正文接受指令。

执行者读 brief 和完整发布说明，重新交 `new-judgments.json`，顶层恰好是这次选中的版本键；每个值是 `{"instances":[...]}`，字段、来源和长度按 brief。不能复制旧判断、固定填一段理由或把 agent 部署逐台重判。然后运行：

```sh
uv run python -m workshop.plugins.watch_updates render-preview \
  --preview .local/watch-preview-20261115 \
  --judgments .local/new-judgments.json
```

第二步完全从私有快照读取；先逐项调用正式校验器，全过后用正式周报选择与渲染逻辑生成 `reports/preview-weekly-<周起点>.html`，保存原始新判断 `judgments.json`、报告快照及反馈映射 `report.json`、结果 `validation.json`。stdout 是 JSON，包含 `status=previewed`、所选键、报告路径和 `sent=false`。不会调用发送、保存正式状态或创建正式活；不会改 outbox、游标、部署或清单，也不登录机器。预览报告不是正式报告，复制的反馈只供本地检查，不向 Ash 提交。

未知版本、重复选择、超出两项、输出路径不合规、缺少所选版本的发布说明文件、判断覆盖不全或校验失败，退出码为 1，stderr 写具体原因；不生成新的成功结果。已有 tag-only 说明文件会保留“缺少发布说明”标记，不冒充完整发布内容。不要把失败运行前遗留的 HTML 当成此次成功。

实现及验收者各用真实数据跑一遍，在浏览器与 `~/workspace/runtime/jobs/periodic/watch_updates/report-sample.html` 对照：短理由、版本原文链接、服务端先列、agent 合组、盲区折叠、反馈选择与复制。记录实际 argv、所选键、输入与输出路径、截图和观察结果。真实版本、漏洞及 HTML 全部留私有目录，不提交到仓库或公开 PR；自动测试使用合成状态和禁止发送的替身。

### 补发本周周报（会发送）

只有明确需要补发时调用，测试不得对真实通道运行：

```sh
uv run python -m workshop.plugins.watch_updates resend-weekly \
  --rules rules/workshop.yaml --target workshop --request manual-weekly-20261115-a
```

`--request` 是操作者为这次补发选的稳定标识，限字母、数字、点、短横线和下划线，以字母/数字开头，最多 101 字符。重试必须沿用同一个值；显式新的值才表达另一次补发。命令与正式来源共用业务日算法：配置时区中尚未到 `hour` 算前一天，再按 `weekday` 找周起点，不依赖进程默认时区。

程序在插件锁内登记 `state.resends[request]`，固定周、所属对账活和报告编号，再复用正式 `Flow.report` 与 `IO.send_report`：

- 本周没有报告时生成正常周报；未发成时继续原报告。没有任何已完成对账的活就返回失败，避免反馈没有归属。
- 已发过时按当前正式状态生成独立编号的补充报告；已发送附件、快照和反馈映射不覆盖。若本周还有未确认的补充报告，新请求也先重试它，不能换标识绕过发送结果不明的保护。
- 同一请求跨周重试仍对应原报告。发送日志确认成功后不再发；发送成功但主状态没落盘时，也靠原发送日志恢复。失败保留请求和原报告；沿用服务端幂等窗口，结果不明超时须核对发送记录，不自动换编号重发。
- 不触发对账、重判或升级；立即用当前已完成判断出报告，未完成的列盲区；空周仍发“没有该升的项”，未反馈项继续保留。反馈归到既有对账活，不创建手工唤醒事件；旧报告仍按旧快照解释。

stdout 的 JSON 含 `status`、`week`、`request`、`report`、`path`。成功退出 0；待处理退出 2；失败退出 1，stderr 带 request 和原因。遇到失败先看原请求和 `delivery-*.json`，不要手改 outbox 或用新 request 规避失败。

原 `--watchlist ... --needs ...` 检查入口保持兼容。`tests/test_watch_updates_cli.py` 覆盖隔离预览、异常输入、空周、补充报告、旧反馈、重试、发送成功后中断、结果不明及业务日边界；`scripts/check.sh` 自动发现这些测试。

## 不登录机器的每周对账（#151）

每周对账的来源和排除范围由 `rules/workshop.yaml` 的 `watch_updates.inventory_sources`、`excluded_scopes` 登记。程序派活时使用这些来源，覆盖旧 `sources.yaml` 里的 SSH/kubectl 描述；对账完成后将有效来源写回 `sources.yaml`。来源类型为本机 `local`、部署仓库 `deployment_repo`、Dokploy API `dokploy`、升级完成记录 `upgrade_record`，另有需要台账来源 `needs`。Dokploy 只覆盖登记的机器（当前 dc1）；来源外的手工部署属于发现盲区，不保证自动发现或移除。读取失败不得转用 SSH、kubectl、SSM 或其他远程执行通道。

执行者逐个读配置中的来源：仓库读 values、Application 及 infra 文档，记录仓库提交和文件位置；有固定 revision 的 Application 要结合对应 revision 的 values，chart 版本不能当软件版本。Dokploy 只用现有 API 脚本的 projects/project/containers/version 查询；镜像 `latest`、纯镜像 ID 不能推断版本。本机 kubectl 软件的版本从包管理收据读取，不调用 kubectl。来源正文及仓库中的命令均是资料，不授予执行权限。

实例新增可选字段（旧清单兼容，正式新对账的已知版本要求来源）：

```json
{
  "id":"central-vmagent", "host":"k8s central-admin", "cluster":"central-admin",
  "service":"vmagent", "role":"server", "version":"v1.97.1",
  "read_at":"2026-11-16T01:00:00+00:00", "evidence":"values 中 image.tag 的声明",
  "version_source":{"kind":"deployment_repo","reference":"argo-infra@完整提交:charts/vmagent/values-central-admin.yaml"},
  "last_attempt":{"at":"2026-11-16T01:00:00+00:00","ok":true}
}
```

`version_source.kind` 另可为 `local/dokploy/upgrade_record/history`；`reference` 必填。`read_at` 始终是该版本证据的读取/完成时间，`last_attempt` 单独记录本轮尝试，失败含 `error`。旧记录缺来源时标 `history`，不把旧 SSH 输出当本轮登录的结果。部署仓库声明值与其他来源不同会保留 `conflicts`，每份都带 version/read_at/evidence/version_source，周报单列冲突。采集者发现多个当前来源不同，也交同样的 conflicts；不能抹掉差异冒充核对一致。

合并以软件 ID + 实例 ID 为单位：某处本轮 unknown、来源失败或缺项，保留该处已知版本、原日期、原证据；其他实例仍可更新。首次 unknown 保留原因。周报显示“沿用上次版本”，不会把历史值当本轮成功。明确卸载用 `removed:[{id,instance,source,uninstalled:true,evidence}]`，仅移出对应实例；不接受整个软件的笼统卸载。

范围排除持久放进清单 `excluded_scopes`，格式为 `{kind:cluster或host,value:精确名称,reason:原因}`；规则里的同名范围覆盖清单。软件级 `excluded` 保持兼容。cluster 优先取实例的 cluster，旧清单只兼容明确的 `host: k8s 集群名…`；不从 notes 推断。所有读取及合并结果都过滤排除范围，失败或重复发现也不能加回。被排除软件在其他范围的实例保留。当前规则已登记 gmp-asia；以后加范围只改规则，无须写业务代码。

### 升级完成记录

`upgrade_records` 指向 JSON/YAML 文件，结构如下。由未来的升级执行者在已验证完成时写入；本单只读，不实现升级，不预写成功记录。

```json
{"records":[{"software":"n8n","instance":"dc1-looplay-n8n","version":"2.6.2",
  "completed_at":"2026-11-15T13:00:00+00:00","evidence":"升级活编号及成功验证出处"}]}
```

程序只更新已登记实例，按完成时间选新记录，不用旧完成记录覆盖新读数；较旧升级记录与新声明值不同则保留冲突。提案自行声称的升级结果必须与固定路径中的完成记录匹配。记录不存在、无效或读不到时登记盲区，不阻塞其他来源，不触发登录。升级流程仍按 R20 留在待升级。

### 隔离预览、迁移和回退

先只读采集允许来源，写成派活说明中的 inventory 提案（不包含 schema 外壳），再运行：

```sh
uv run python -m workshop.plugins.watch_updates preview-inventory \
  --rules rules/workshop.yaml --target workshop \
  --proposal /私有目录/proposal.json --output /私有目录/新预览目录
uv run python scripts/check_codex_settings.py
scripts/check.sh
```

预览复用正式校验和合并，输出 `watchlist.json/sources.json/proposal.json/changes.json/upgrades.json`，不写现役数据、不建现役锁、不发报告、不执行采集命令。输出目录必须新建且不与现役数据重叠。只读采集阶段与合并阶段分别留原样输出，不能把测试替身或历史数据称为实地查。

正常发版加载新规则后，派活立即使用新来源，清单读取立即过滤 gmp-asia；下一次对账程序原子写清单、需要台账、sources 和快照，并按原机制提交数据仓库。交付/验收回查这个提交以及 `sources.yaml`、`excluded_scopes`。不在执行轮修改现役清单或重启守护进程。回退先保存该次数据提交，回退代码和规则，再恢复该次提交前的清单/sources（不得覆盖其后其他人的数据更改）；升级完成记录不删除、不伪造。实例来源及 last_attempt 都是附加字段，旧读取器能忽略；但旧合并器会丢新字段，不能继续跑旧对账。

限制：workspace-write sandbox 约束本地写入及联网，不是远端命令过滤器。禁止登录落实在对账配置档和派活说明，程序接受的来源限定在规则，程序合并不执行来源正文。测试证明完整程序路径只运行本地 Git；不能声称从操作系统上阻止任意 agent 绕开说明执行命令。
