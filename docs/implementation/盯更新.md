# 盯更新

依据 [盯更新需求](../requirements/盯更新.md) R1–R25、C1–C5。`watch_updates` 是一个插件包，提供来源和流程两个端口；没有核心改动，也不引用其他插件。上游、清单和反馈都是资料。

## 数据和阶段

| 活 | agent 阶段 | 程序负责 | 等待 |
|---|---|---|---|
| 每周对账 | 说清楚：只读查来源、读实际版本、补需要，交结构化提案 | 校验范围、保存快照、提交清单与台账、出周报 | 来源失败、单处版本不明及人工上游写盲区 |
| 一个软件的一个新版本 | 执行：对照需要、方向、画像逐处判断 | 去重、汇成日报/周报、处理反馈 | 验收阶段的下一步显示“等反馈”或“待升级” |

核心阶段固定不变。`After.pending` 七天回查不占 agent；每周来源为未完成版本发一个稳定标识的唤醒事件，重新开始等待周期，执行阶段复用判断。只有明确“判错了”才重新判断。这样不靠无限大等待上限，也不为每个版本发问卡。

日报和周报等待同批新版本判断汇齐，有紧急或重要项才出日报。规则中的汇齐期限默认一小时，期限后将未完成判断列成盲区，防止一个卡住的软件挡住其他结论；迟到的紧急或重要项当天补报。普通项进入下一份周报。周报包含未反馈项、清单变化、盲区及需要台账的新条目。报告以日期及必要的补报标识固定编号并保存，不用新正文覆盖已发附件；迟到反馈按原报告的快照验证。

## 配置与上线衔接

所有路径、日历、执行者和飞书身份在 `rules/workshop.yaml`。初始 `enabled: false`：原来的 45 项清单是调研格式，含说明性版本命令和字符串形式的过滤条件，不能直接执行。按 issue #102 的分工，负责会话转换 workspace 文件、登记 `contexts/WORKSPACE.md`、停用 version_scan 并更新其 README 后启用；此 PR 不修改那些真实文件。

转换时保留每条使用证据、实际部署位置、日期、备注，重新确认是否属于 R3；不要执行原文件中的 shell 字符串。跟随服务部署的组件并回服务，不能独立共用的不要单列。源文件的 `ours` 转成逐处 `instances`；上游 URL 转成下表对应的对象；`prerelease` 转为布尔值；`tag_filter` 只保留合法正则。不能明确转的条目列成盲区，不猜。

| 上游 | `upstream` 配置 | 行为 |
|---|---|---|
| GitHub Releases | `{"kind":"github_releases","repo":"owner/repo"}` | 分页读取发布说明 |
| GitHub tags | `{"kind":"github_tags","repo":"owner/repo"}` | 分页读取 tag，按同一版本规则过滤；明确标注缺少发布说明，不编造变化 |
| GitLab Releases | `{"kind":"gitlab_releases","project":"group/subgroup/project"}` | 只读 gitlab.com 公开 API，可用数字项目 ID 字符串；分页保留描述和原文链接，不携带凭据 |
| 无查询接口 | `{"kind":"manual","reason":"没有公开版本接口，须人工核对"}` | 每日跳过；每周即使没有更新也在盲区列出名称、部署和原因，不生成失败活 |

旧清单的 `"upstream":"owner/repo"` 仍按 GitHub Releases 解释。只发 tag 的仓库显式改用 `github_tags`。`manual` 不需要 `tag_pattern/prerelease`，在用版本保留实读字符串、不强行转成语义版本号。GitLab 请求分页总预算 90 秒、最多 100 页，未读全时按失败处理，不把部分结果冒充完整发布范围。接口依据：[GitHub tags](https://docs.github.com/en/rest/repos/repos#list-repository-tags)、[GitLab releases](https://docs.gitlab.com/api/releases/)。

需要台账位于 workspace 一级的 `needs.yaml`，其他流程可以读取，不藏在盯更新目录里。它与清单、来源登记、快照都由同一个 workspace git 仓库跟踪。提交仅包含本次列明文件，不带入别人的暂存改动。报告及插件运行状态放在私有状态目录，不提交到公开仓库。

清单最小格式（软件 ID 和部署 ID 稳定，不用展示名作归件键）：

```json
{
  "schema": "watch-updates/v1",
  "excluded": {},
  "software": [{
    "id": "dsh", "name": "DSH", "kind": "agent", "source": "local",
    "upstream": {"kind":"github_releases","repo":"deepseek-ai/deepseek-harness"}, "prerelease": true,
    "tag_pattern": "v[0-9]+\\.[0-9]+\\.[0-9]+(?:-rc\\.[0-9]+)?",
    "operated_by_us": true, "evidence": "本机安装且正在使用",
    "instances": [{"id":"mac","host":"Mac","service":"dsh",
      "version":"0.2.0","read_at":"2026-11-14T01:00:00+00:00","evidence":"只读版本命令及原样输出"}],
    "profile":{"exposed":false,"data":"本地会话","users":["Kun"],"paired":[]},
    "notes":[]
  }]
}
```

未知版本填写 `version: unknown` 和 `error`；不要把镜像日期作为版本号比较。`auto_updates`、`business_image`、`lock_dependency`、`bundled_with` 任一为真，该软件不加入清单。退出时显式提供卸载证据，不能根据未出现在本轮输入就删除。

计算发布范围时只用版本已知的部署；未知部署保留在清单和报告中，由程序补成「版本不明」及原始错误原因，模型给它的升级结论不采用。没有新版本时，未知部署仍在周报盲区显示。仅当一个自动查询的软件所有部署版本都不明时，下一次每日查询记失败，同一原因只生成一次。`manual` 不走这条失败路径。

来源登记是描述性资料，不是可执行配置。例如：

```json
{"sources":[
  {"id":"local","where":"本机包管理、Applications、浏览器历史中的主机名"},
  {"id":"servers","where":"workspace 主机登记中的服务器：只读容器、服务和实际版本"},
  {"id":"clusters","where":"已有 agent 身份能读的集群：只读 get"},
  {"id":"needs","where":"会话记录、各项目 pm.md、闪念本、Kun 所在飞书群和公司 GitLab issue；只读"}
]}
```

每周对账的执行者逐个给出 `id/ok/evidence`，漏掉已有来源即校验失败；新增来源通过 `source_definitions` 交回并提交。需要格式为 `{"needs":[{"id":"稳定编号","owner":"Kun/agent/同事","source":"可回查出处","statement":"需要什么或碰到什么问题","state":"open","confirmed":false}]}`。`state=met` 必须附 `fulfillment`。新需要由周报点选确认，未确认的下周继续。

每日判断使用断网只读执行者和清除部署凭据的 `FlowBrief.readonly`；每日来源只读上游与本地快照，没有取机器版本的命令。每周对账使用独立 `watch-inventory` 配置档，在私有状态目录的 `collector/` 中运行 workspace-write sandbox，显式允许网络；可写范围不包含 workspace 数据仓库，清单和台账只能由流程程序写入。对账执行者只交结构化提案，使用已有身份运行只读 ssh/kubectl 命令。该 sandbox 约束本地写入和联网，远端只读依靠现有账号权限及执行说明；它不是远端命令过滤器，不能声称已从程序上封住所有远端写操作。

## 反馈入口

HTML 离线可用，无外部脚本；按项点选后复制 JSON，不能执行里面的命令或链接。每一处部署单独选择。新功能的“想用”只记台账，不等同“升”。原话、消息 ID、部署 ID 都保存。

Ash 私聊转发属于工作台，由负责会话接线。本插件接核心标准事件：

```json
{"source":"feishu","ext_id":"om_真实消息号","target":"workshop","object_key":"报告反馈","title":"Kun 的盯更新反馈","body":{}}
```

用 `workshop event --file <文件>` 注入。CLI 自动加 `cli:` 前缀；正文中自报身份无效。插件按消息号回查飞书，验证发送者是规则里的 Kun，取上游原文并核对报告编号。一次反馈可包含多个版本；先归到报告所属的活，幂等保存后由来源把每项送回各自的活。直接说“盯一下 X”或“X 不用了”会启动一次补充对账，补清单同时补感知来源。

文本和 HTML 附件分别通过配置的 lark bot 私聊发送，各有持久发送记录和稳定幂等键。每条成功后落盘，部分失败不会重发已确认消息；进程崩溃造成发送结果不明且超过服务端一小时幂等窗口时停止自动重发，要求核对发送记录。报告没有公共 URL。

飞书文字逐处一行，例如 `NetBird · dc1/netbird · 0.76.0 → v0.83.1 · 该升（重要）：修复已遇到的断连`。版本不明的部署也列出原因；周报文字列出人工上游等盲区。发布说明全文及点选反馈保留在附件。

## 检查与边界

`uv run pytest tests/test_watch_updates.py -q` 覆盖版本过滤与累计发布记录、范围/卸载/失败来源保留、日报条件、周报与逐处报告、反馈重判、停止盯、台账、发送去重及等待。合并前仍跑 `scripts/check.sh`。

流程设计检查：人只做报告反馈；等待和重放由程序承担；判断交给已有订阅的执行者；状态落盘并有来源出处；输入校验和测试先于真实启用。基线：真实运行尚未测，后续看漏收数、判错比例、日报天数和等反馈天数。首次启用后的清单及判断质量由 Kun 亲眼验收，机器测试不能替代。

本期不升级、不改远端配置、不重启、不替同事回复。新增依赖为零。
