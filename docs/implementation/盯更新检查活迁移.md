# 盯更新检查活迁移

对应 #177、盯更新 R19/R20/R21。来源游标仍按软件版本去重，入核心前将 version、reconcile、failure 归到当前检查活；逐项判断的键不再是活的键。第一件是 `workshop:watch_updates:check`，收尾后的下一件是 `check:2`，依次递增。收尾钩子与核心完成状态之间的窗口，经规则中的 `core_database` 只读回查，仍归到原检查活。

同一检查活在执行阶段依次做对账和判断，每轮只处理一个 task_key。取不到资料时将 blocked 原因留在该项，继续其他项；每周对账可以让失败的判断重新尝试。原有报告渲染、部署分组、需要台账和升级完成记录读取不变。旧报告在检查活已收尾后收到新反馈时，归到当前检查活；没有活动检查活则开下一件，不能复活第二件活动检查活。

检查项完整资料写在插件状态目录的 `events/`，核心材料带稳定记录标识；迁移历史完整档案在 `migration/`，`why --raw` 展示原状态、阻塞和档案路径。派活保留这些索引，只展开本轮要处理的一项，避免把全部历史塞进每轮提示词。报告截止时间到达后先发已判断项，继续处理剩余项；迟到的紧急项仍补日报。

选「升」后的请求先落入插件 outbox，再由来源可靠地交给核心。键为 `upgrade:<软件>`；同一软件所有选中部署合在一件升级活，资料保留版本、部署快照、报告选择及原话。升级活自动到验收阶段，下一步显示「待升级」，不调用升级、远程登录或重启命令。

## 首次上线

规则 `watch_updates.consolidate_on_start: true` 让 `workshop run` 在开启第一拍前调用插件迁移。迁移成功前来源不推进游标。只在首次迁移时复制数据库和插件 state.json，目录为数据库旁的 `watch-updates-backup-<UTC时间>`；备份路径和迁入旧活列表原样打印到启动日志。首次备份时间随数据库大小变化。按定时发版 R3 和 Kun 对 Q1887 的批准，仅 #177 首次迁移允许一次不超过 30 秒的维护窗口；以旧守护进程最后一次心跳到新守护进程第一次心跳计，验收须记录实际停启时间、迁移输出和恢复状态。此后发版仍执行 1 秒上限。本机真实副本测试不等于上线验收。

迁移拒绝存在未结算旧轮、程序作业或未回答等待的状态，不绕过这些关口。失败原因打印到启动日志，盯更新来源保持暂停，旧活标为待迁移；其他流程照常启动。结算旧轮后须在下一停机窗口重试；上线前应确认旧盯更新活没有正在跑的轮次。

迁移只追加核心事实：活动旧活转为已并入的历史项，取消旧定时和未完成效果，给每个旧键登记检查活别名。原本完成、放弃的活完全不改。检查活资料保存每件旧活的原阶段、状态、阻塞、历史结论、版本判断、反馈和原始材料；`workshop why <旧键> --raw` 经别名查到这些资料。报告原 anchor 留作 previous_anchor，并改为检查活。

数据库事务前先保存可重复合并的插件状态；事务提交后再标记迁移完成。中途退出可以原命令重跑，不重复复制材料、不生成第二件检查活。不能只恢复其中一个状态文件。

## 副本验证

使用 SQLite backup API 复制真实数据库，并复制同一时点的盯更新 state.json；不要仅复制可能仍有 WAL 的主数据库文件。副本目录里的路径全部显式传入。下面两次命令须使用同一副本，第二次应输出 `{"status": "unchanged", "migrated": 0}`。

```sh
uv run python -m workshop.plugins.watch_updates migrate-checks \
  --rules rules/workshop.yaml --target workshop \
  --database /绝对路径/副本/workshop.db \
  --watch-state /绝对路径/副本/watch_updates --offline

uv run python -m workshop.cli --state-dir /绝对路径/副本 status --flow watch_updates
uv run python -m workshop.cli --state-dir /绝对路径/副本 why workshop:watch_updates:check --raw
```

`--offline` 表示该数据库没有运行中的守护进程。真实库手工迁移也只能在停机窗口使用，不能在运行中用此命令抢改；自动启动迁移无需人工运行该命令。迁移命令不发报告、不升级、不改盯更新清单或需要台账。

## 验收与回退

执行轮验证副本；上线后的验收另外核对真实启动日志、备份路径、唯一活动检查活及旧键别名，逐项核对迁移前等反馈项的归属。必须等一次真实每日检查或真实每周对账，确认后续事件仍归检查活。未到检查时间用 later 登记下次验收；不能用测试事件冒充真实来源，也不能伪造 Kun 的「升」反馈。

若需要退回旧代码，先停止守护进程，再从同一备份目录同时恢复数据库和插件状态；恢复前另外备份新状态，避免丢失迁移后收到的事件和反馈。已产生新反馈时须先对账再回退，不能仅回退 Git 提交后让旧流程处理新检查活。执行者不得自行恢复生产库。
