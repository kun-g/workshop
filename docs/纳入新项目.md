# 纳入新项目

给新仓库接入 issue 交付时按下面清单做。交付对象是车间要交付到的仓库；短名用于 `workshop check-issue '短名#号'` 等命令。规则入口只有 [rules/workshop.yaml](../rules/workshop.yaml)，issue 的内容标准见 [issue 写法](issue写法.md)。

## 1. 登记交付对象

在 `targets` 下加一个独立名字，填 `repo`（owner/repo）、唯一 `short_name`、只读主检出的 `checkout`、`requirement_docs`、`sources`，并配置 `default_flow` 和 `flows.issue_delivery` 的阶段、触发器。沿用规则现有 `issue_triggers`，让 GitHub 的 issue 更新进入接单核对；需要定时发版的按第 5 步补对应流程和来源。流程内的配置覆盖交付对象配置，自检也读取 issue 流程的覆盖值。

`requirement_docs` 登记仓库内文件或以 `/` 结尾的目录；目录递归读取 Markdown。检查默认要求 `scripts/check.sh`，项目使用等价命令时在 `required_checks` 写 argv 列表，并在 issue 中使用同一命令。执行者、身份、检查超时和串行路径按该项目需要配置，字段含义见 [插件端口](implementation/ports.md)。

确认：在车间 worktree 运行 `scripts/check.sh`，规则能加载；逐项核对仓库、短名、需求路径、流程和触发器均指向新项目。第 6 步再用新短名做实际自检。

## 2. 写需求文档

在项目仓库建 `docs/requirements/`，用 `align-requirements` skill 与 Kun 对齐需求；经确认的要求写成行首 `**R数字` 或 `**C数字` 的条目。将文档合入默认分支后，issue 才能引用它们。文档名相同的，用仓库根起的完整路径区分。

确认：用项目的 App 身份从 GitHub 默认分支读取每份登记文档，核对正文和编号；第 6 步用「文档名 R编号」的真实引用跑自检。自检不采用本地工作区的需求文档。需求变更如何带原话、在同一个 PR 改文档，按 [issue 写法的依据节](issue写法.md#依据) 办。

## 3. 加 issue 模板

在项目仓库的 `.github/ISSUE_TEMPLATE/` 加模板，按 [issue 写法](issue写法.md) 的顺序放六节标题及填写提示；可从 [车间模板](../.github/ISSUE_TEMPLATE/issue-delivery.md) 起步，替换短名和检查提示。保留「待补充」提示，直到作者写出具体条件，避免模板原文被当成写全。上线后才能测的条件另加「上线后 DoD」，每项有能跑的检查。

确认：`workshop check-issue --file <模板路径> --target <短名>` 退出 1，列出待补项；模板合入默认分支后，在 GitHub 新建 issue 页能选到它。

## 4. 配 App 身份

将 GitHub App 安装到新仓库，并在 `agent_github_identity` 的配置 `~/workspace/runtime/tools/agent_github_identity/config.json` 登记仓库与 `repo_permissions`。安装范围和本机签发权限都要覆盖仓库；仅改其中一个不够。按实际流程授予 contents、issues、pull_requests 的读写权限及检查状态所需的读取权限。

在交付对象的 `github_identity` 配 `mode: app`、真实 `gh` 绝对路径和签发器 argv，沿用现有配置格式。需要跨仓库读关系时另核对 `relations_identity` 的范围。安装或扩大权限按已有授权边界办理。

确认：用该配置签发并调用只读仓库、issue、需求文档接口，自检能成功；核对签发记录中的仓库和权限，不打印令牌。App 签发失败应直接报错，不回退到 Kun 的个人身份。身份工具的操作细节见其 `README.md`。

## 5. 确认发版方式

按项目实际交付条件选 `release` 和 `deployment`：

- 合并即交付的用 `release: none`。若 issue 有上线后 DoD，仍需配置实际线上版本的回查方式。
- 定时批量发版的，在 `flows.scheduled_release` 配发布流程、`sources.main_branch` 配比较周期。集群项目的 issue 流程用 `release: scheduled`，并在 `deployment` 配线上应用、分支、源提交字段和 rollout；本机车间的配置示例是 `release: none` 加 `deployment: {kind: running}`。
- 用 tag 驱动发布的，核对 `release: tag`、`tag_command` 和线上版本回查。不要照搬另一个项目的发布脚本或集群名字。

确认：发布流程与 issue 流程各自负责什么已写清，配置检查通过；第一次经授权发版后，`workshop why '<短名>#<号>'` 的证据显示线上版本包含该合并提交，且上线后检查通过。具体字段及行为见 [issue 交付实现](implementation/issue-delivery.md) 和 [定时发版](implementation/定时发版.md)。

## 6. 自检后交给车间

先用一份真实草稿跑：

```sh
workshop --rules rules/workshop.yaml check-issue --file /绝对路径/草稿.md --target <短名>
```

写全并开出 issue 后再跑 `workshop check-issue '<短名>#<号>'`，也可用 `workshop check-issue '<交付对象>:<号>'`。命令只读：不建活、不打标签、不评论、不打开状态库；从规则和 GitHub 默认分支取资料。`--rules` 或环境变量 `WORKSHOP_RULES` 指向要核对的规则；省略时使用当前安装的车间代码旁的 `rules/workshop.yaml`。

确认：写全时退出 0，打印能跑的检查；缺项退出 1，每行缺项与接单「等资料」的 next 一致；用法、读取或身份失败退出 2，先解决读取问题再核对。规则随车间正常发版启用后，从 `workshop status` / `why` 确认 issue 按配置进入接单。写全会自动开工，还没定的内容留在草稿里。
